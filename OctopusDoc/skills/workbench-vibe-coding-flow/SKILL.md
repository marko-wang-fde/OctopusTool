# Workbench Vibe Coding Flow

Use this skill to create and verify Workbench React business apps across local development, Octopus digital-employee containers, and hosted Workbench deployments.

## Target State

There is one successful path:

- Use `octopus-cli coding` as the only Workbench Vibe Coding project lifecycle entry.
- Initialize with `npm create @syngy/workbench-app-react@latest <app> -- --features arcubase`.
- Generate Arcubase TS SDK with `npm run arcubase:codegen`.
- Use `@syngy/workbench-auth` and `@syngy/workbench-devtools` for Workbench login state, token refresh, redirect, and Host requests.
- Access Arcubase through the Host generic proxy endpoint ending in `/arcubase/api`.
- Read and write business records through the TypeScript SDK generated by `npm run arcubase:codegen`.
- Render the first screen as the real business app surface. Local login is handled by the devtools login page.
- Ship a usable business product surface: navigation, search/filter, sync, create, save, and other visible primary commands have implemented behavior.
- Use generated ingress `can()` helpers to decide whether route buttons, menus,
  forms, and editable fields are visible or enabled.

## Required Package Roles

- `@syngy/create-workbench-app-react`: scaffolds the app shell, business routes, data access sample, and `arcubase:codegen`.
- `@syngy/workbench-auth`: owns Workbench runtime/session loading, token refresh, `createWorkbenchFetch`, and Host request auth.
- `@syngy/workbench-devtools`: owns the local standalone login page at `/__workbench/login` and JCode handoff UI.
- `@syngy/workbench-arcubase-codegen`: generates local TS SDK from Arcubase ingress and entity schema.
- `@syngy/arcubase-client`: provides the app-side Arcubase client.

The generated app uses the shared runtime packages at runtime. `octopus-cli coding` is used for project lifecycle commands outside the app.

## Real Data Integration Contract

Successful Workbench Vibe Coding means the business UI is connected to the
Arcubase app selected in preflight. Treat codegen output as the application data
boundary:

- Generate the SDK first, then build data adapters around generated ingress
  clients and generated entity field types.
- Treat each generated ingress client as one complete Arcubase ingress policy:
  the policy id, Arcubase action names, field ids, field read/write permits, and
  query condition are internal to that generated client.
- Each primary business route reads its visible rows through the generated SDK
  clients. Business route data must render rows returned by Arcubase queries.
- Create and update workflows call generated SDK actions for the matching
  Arcubase ingress.
- UI command visibility is derived from generated ingress `can()` helpers:
  `customers.can('create')` for create buttons, `customers.can('update', { field:
  'owner' })` for editable fields, and `customers.can('view', { field:
  'companyName' })` for readable field surfaces.
- Visible create and update controls are complete workflows: open a business
  form, validate required fields from generated schema, call `prepareCreate`,
  `create`, or `update` on the generated ingress client, show loading and
  backend errors, then refresh the Arcubase query result after success.
- Visible search, filter, navigation, sync, export, notification, and other
  commands either perform the named business action or are omitted from the
  primary business surface until implemented.
- Counts, KPIs, pipeline totals, status badges, and table rows are computed from
  returned Arcubase records.
- When Arcubase returns zero rows, show a true empty state and zero counts for
  that entity.
- Local constants are appropriate for route definitions, labels, table column
  metadata, and empty-state text.
- SDK/schema/ingress metadata proves codegen readiness only. It is not evidence
  that visible business data is synced.
- Project notes must record which generated ingress powers each route and the
  observed Arcubase row count during validation.

Validation must include source evidence that visible business data flows through
the generated SDK, for example imports from `src/arcubase`, calls to generated
query/action clients, generated ingress `can()` checks for visible commands, and
UI state populated from those calls.

Validation must also include product-operation evidence for the first screen:
clickable primary commands open their expected UI, form submission reaches the
generated SDK write action, backend errors are surfaced in the workflow, and
successful writes reload the queried Arcubase data.

## Preflight

Before creating or editing code, verify the platform context:

```bash
octopus-cli --version
octopus-cli auth profiles current --json
octopus-cli auth whoami --json
```

Confirm:

- The active profile points to the intended Octopus tenant/Host.
- The selected team is the intended team.
- The current user can manage Workbench Vibe Coding projects for that team.

Profile decision rules:

- Treat the active profile at preflight start as the selected profile unless the
  human explicitly provides another profile name.
- Do not switch profiles automatically after scanning local profiles.
- Do not infer the required Host/profile from `--web-url`; the codegen web URL
  is the JCode handoff page origin, not the Octopus API profile target.
- If `octopus-cli auth whoami --json` fails for the active profile, stop
  preflight and report the exact login command for that same profile, for
  example:

```bash
octopus-cli auth login --profile <active-profile> --web-url https://app.autostaff.cn
```

- If `whoami` exposes a team role and the role is not `admin`, stop before
  creating or publishing and ask the human to select a profile with Workbench
  project management permission.

Then identify the Arcubase app that the Workbench app will use:

```bash
octopus-cli configure arcubase list --json
```

Record the Arcubase binding for the selected team, then record the business
Arcubase `appId` from the requirement or the Arcubase app URL. The binding check
confirms that this team can reach Arcubase; the business `appId` identifies the
schema used by the generated Workbench app.

Clarify the business requirement before development:

- Product category and target users.
- Primary routes and workflows.
- Arcubase entities that power each route.
- Expected create/read/update actions.
- Hosted Workbench validation route, usually `/dashboard`.

Write these decisions into a short project note in the app repository before
implementation, including the real data route-to-ingress mapping, for example:

```text
docs/workbench-vibe-coding.md
```

## Create Project

Local user:

```bash
npm create @syngy/workbench-app-react@latest my-workbench -- --features arcubase
cd my-workbench
npm install
octopus-cli coding templates list --json
octopus-cli coding projects create --type workbench --title "My Workbench" --description "Business workbench app" --json
```

Octopus digital employee container:

```bash
npm create @syngy/workbench-app-react@latest my-workbench -- --features arcubase
cd my-workbench
npm install
octopus-cli coding templates list --json
octopus-cli coding projects create --type workbench --title "My Workbench" --description "Business workbench app" --json
```

In a digital-employee container, the platform-provided identity is used by the shared packages and CLI.

After `npm create`, treat the generated app directory as the only project root
for this flow. All app files, project notes, generated SDK files, tests, builds,
and `dist` publishing must be under that generated app directory. Do not write
project artifacts into the parent validation directory.

## Arcubase Codegen

Run:

```bash
npm run arcubase:codegen -- --app-id <arcubase-app-id> --out src/arcubase --web-url https://app.autostaff.cn
```

Expected modes:

- Container/digital employee: `arcubase-admin-env`, using injected Arcubase admin environment.
- Local developer machine: `host-jcode`, using local Workbench JCode authorization and cached refresh token.

Codegen must load the ingress list first, then deduplicate entity lookups to fetch schema details. For Host access, use the generic Arcubase proxy base:

```text
/api/v1/teams/:teamId/arcubase/api
```

## Local Development

Start:

```bash
npm run dev
```

Validation behavior:

1. Visit a business route such as `/dashboard` with no local Workbench login state.
2. The app redirects to `/__workbench/login?return_to=<original-route>`.
3. The login page is served by `@syngy/workbench-devtools`.
4. Complete the JCode flow on the Account/BotWorks authorization page.
5. Click the dev login page completion action.
6. The browser redirects back to the original business route.

The resulting page should show:

- Business navigation and content.
- Current user identity in the header.
- Arcubase row counts that match the selected backend entities.
- Business tables/lists populated from generated SDK query results, or true
  empty states when the backend has zero rows.

## Hosted Workbench Validation

Publish with the project created by `octopus-cli coding projects create`:

```bash
npm run build
octopus-cli coding projects publish <project-id> --path dist --json
octopus-cli coding projects watch <task-id> --json
```

For a deployed `*.workbench.autostaff.cn` app:

1. Directly visit `/dashboard`.
2. Reload `/dashboard`.
3. Navigate through the app sidebar to `/customers`.
4. Reload `/customers`.

Each state should show:

- Current logged-in user identity in the header.
- Business application surface.
- Arcubase row counts that match the selected backend entities.
- Business tables/lists populated from generated SDK query results, or true
  empty states when the backend has zero rows.

Hosted apps use existing Workbench cookie/localStorage access token state through `@syngy/workbench-auth`.

## Verification Commands

Use command-line checks as the primary validation path.

In the generated or target app:

```bash
npm test
npm run build
```

Verify the real data path in source:

```bash
rg -n "from './arcubase'|from './arcubase/|createSyngyClients|\\.query\\(|\\.prepare\\(|\\.execute\\(" src
rg -n "sample[A-Z]|mock[A-Z]|fixture|demo data|hard-coded customer|hard-coded opportunity" src
rg -n "prepareCreate|\\.create\\(|\\.update\\(|onClick|onSubmit|onChange" src
```

The first command should show the generated SDK imports and query/action calls
used by business views. The second command is a review aid: any match should be
business-neutral scaffolding, tests, or clearly non-rendered metadata; visible
business rows must come from Arcubase query results.
The third command should show that visible commands and forms are backed by
event handlers and generated SDK write actions.

Publish and watch the hosted deployment:

```bash
octopus-cli coding projects publish <project-id> --path dist --json
octopus-cli coding projects watch <task-id> --json
```

After `watch` returns a Workbench URL, check the hosted route surface through
HTTP:

```bash
curl -sS -o /dev/null -D - https://<app>.workbench.autostaff.cn/dashboard
curl -sS -o /dev/null -D - https://<app>.workbench.autostaff.cn/customers
curl -sS -o /dev/null -D - https://<app>.workbench.autostaff.cn/opportunities
```

Expected unauthenticated HTTP result is the Workbench auth redirect with the
original route preserved in `state.returnPath`, not `404 page not found`.

Run package checks when changing the shared packages:

```bash
npm --prefix syngy-packages test
npm --prefix packages/create-workbench-app-react test
```

## Explicit UI Smoke

Do not use browser automation in the primary CLI validation flow. Use command-line
checks for automated validation. Use a browser only when the human explicitly
asks for interactive visual inspection in the current task.

Local:

- `http://127.0.0.1:<port>/dashboard` redirects to `/__workbench/login` when login state is absent.
- JCode authorization redirects back to `/dashboard`.
- Sidebar route click changes to `/customers`.
- Header shows the current user and role.
- The page shows business content and Arcubase sync state.
- Search input changes the visible business rows.
- New customer visibility is controlled by `customerIngress.can('create')`;
  clicking it opens a business form, submit calls the generated customer ingress
  create action, and the customer query result refreshes after success.

Hosted:

- `https://<app>.workbench.autostaff.cn/dashboard` opens directly.
- Reload keeps `/dashboard`.
- Sidebar route click changes to `/customers`.
- Reload keeps `/customers`.
- Header shows the current user and role.
- The page shows business content and Arcubase sync state.
- Search input changes the visible business rows.
- New customer visibility is controlled by `customerIngress.can('create')`;
  clicking it opens a business form, submit calls the generated customer ingress
  create action, and the customer query result refreshes after success.

## Common Failure Diagnosis

- `octopus-cli coding ...` fails with profile/team/auth errors: run the preflight commands again and switch to the intended profile/team before continuing.
- `npm create @syngy/workbench-app-react@latest ...` generates stale package content: verify the published `@syngy/create-workbench-app-react` version and npm initializer cache before continuing.
- Container codegen asks for JCode: codegen selected the local `host-jcode` mode; use the container Arcubase admin identity mode.
- Local dev shows auth panels in the business page: keep login UI in `@syngy/workbench-devtools`.
- Right header has no current user: verify Workbench runtime viewer first, then Host `/api/v1/me` through `createWorkbenchFetch`.
- Arcubase calls miss `/arcubase/api`: fix runtime endpoint/proxy base; keep the generic proxy path.
- UI shows business rows while Arcubase admin shows zero rows: visible data is
  not wired to generated SDK query results. Rework the route data adapter so the
  same generated SDK ingress used in codegen supplies the rendered rows.
- A visible business button has no response: the product-operation contract is
  incomplete. Wire the command to the generated SDK workflow or remove it from
  the primary surface for this iteration.

# Team 内数字员工方案设计

FDE 方案的运行边界是 team。数字员工不是脱离 team 的孤立对象，它服务 team 内的人、数据、设备、Secret、计划任务、知识和业务系统。

## 方案设计顺序

1. 先写业务闭环：客户希望哪个日常工作被持续完成。
2. 再定服务对象：谁发起，谁接收结果，谁负责查看异常。
3. 再定数字员工：一个员工负责一个清晰岗位结果。
4. 再定能力组合：员工为了完成岗位结果，需要哪些 toolkit 和配置。
5. 最后定验证路径：如何在 team 内证明它能跑通。

## 员工设计卡

每个数字员工都应有一张设计卡。

| 字段 | 填写要求 |
| --- | --- |
| 员工名称 | 业务用户能理解的岗位名 |
| 服务对象 | team 内哪些成员或角色会使用它 |
| 业务职责 | 它负责交付什么结果 |
| 不做范围 | 明确哪些事不归它处理 |
| Cue | 由对话、任务、计划任务、Webhook、邮件中的哪些入口触发 |
| Reference | 需要哪些 skill、文档、知识库、WebSkill 或数据结构 |
| Input | 运行时需要哪些字段、文件、业务对象和上下文 |
| Do | 需要哪些能力完成动作 |
| Output | 结果落到哪里 |
| 能力状态 | 说明该能力已在类似场景稳定使用，还是需要先做试点验证 |

## team 级配置清单

FDE 设计方案时，应把配置对象分成 team 级，而不是写成平台全局概念。

- 成员和业务角色：谁能配置、谁能使用、谁接收结果。
- 任务看板：任务如何创建、分派、推进和完成。
- 计划任务：哪些周期动作需要自动触发。
- 设备：哪些设备可被员工使用。
- Secret：哪些凭据由保险箱管理。
- 浏览器和 WebSkill：哪些网页系统需要登录、操作和沉淀经验。
- 内网服务：哪些用户内网或私有服务需要被访问。
- 知识库同步：哪些资料进入员工可用知识范围。
- Vibe Coding：是否需要为该 team 构建 Workbench 应用。

## 方案输出

一个 team 方案至少输出四份材料：

- 场景 CRIDO 表。
- 员工设计卡。
- 能力组合表。
- 最小验证用例。

# CRIDO 场景分析法

CRIDO 用来把客户需求从一句模糊愿望拆成可开发、可验证的场景模型。

```text
Cue -> Reference -> Input -> Do -> Output
```

在本项目中，CRIDO 的具体含义如下。

| 环节 | FDE 要回答的问题 | Octopus 中对应的能力线 |
| --- | --- | --- |
| Cue | 什么事件、入口或时间点让员工开始工作 | 对话、任务看板、计划任务、Calendar Sources、Webhook、电子邮箱 |
| Reference | 员工依据什么规则、知识或流程执行 | skill、知识库同步、业务文档、WebSkill、Arcubase 结构 |
| Input | 本次执行拿到了哪些上下文 | 用户文本、任务字段、邮件内容、Webhook payload、日历上下文、文件、业务记录 |
| Do | 员工通过什么方式实际完成动作 | browser_use、compute_use、Secret、设备、内网服务、Vibe Coding、octopus-cli、Arcubase |
| Output | 用户或系统最终看到什么结果 | 任务进展、消息、文档、表格、应用、数据写回、网页系统状态变化 |

## Cue：触发方式

Cue 只描述「员工如何开始」。不要把触发方式和执行能力混在一起。

常见 Cue 包括：

- 对话：用户在 Portal 或外部渠道直接提出问题或派发任务。
- 任务看板：用户或其他流程创建任务，由某个 team 内数字员工处理。
- 计划任务：按固定时间、周期或日历上下文触发。
- Webhook：外部系统事件进入 Octopus。
- 电子邮箱：邮件或附件进入员工处理流程。

Calendar Sources 应挂在计划任务下理解。它不是一个独立业务能力，而是让计划任务知道节假日、工作日、排班或业务日历上下文。

## Reference：执行依据

Reference 是员工执行时要遵循的依据，不是工具本身。

FDE 应优先沉淀四类 Reference：

- skill：稳定作业流程、触发条件、工具使用方式和结果格式。
- 业务文档：规则、口径、例外处理、客户偏好。
- 知识库：可检索资料、产品说明、历史材料、FAQ。
- WebSkill：某个网页系统的可复用操作经验，应挂在 browser_use 下。

## Input：输入上下文

Input 必须能被实际读取或传入。方案中不要写「系统自动理解全部上下文」这类不可验证描述。

FDE 在写 Input 时应列清：

- 用户输入：文本、图片、附件、表格。
- 事件输入：Webhook 字段、邮件主题和正文、任务字段。
- 业务输入：客户、订单、项目、设备、工单等业务对象。
- 权限输入：触发人、执行员工、team 内角色和可访问范围。

## Do：执行路径

Do 是员工真正改变业务状态或生成结果的路径。常见执行能力包括：

- 浏览器能力：进入网页系统查询、下载、填写或提交。
- WebSkill：沉淀高频网页操作流程，归属于浏览器能力。
- compute_use：需要桌面环境、长任务或隔离计算时使用。
- Secret：使用系统所需凭据和秘密，避免把账号密码写入 skill。
- 设备：管理可供系统使用的 team 设备。
- 内网服务：与用户内网或私有服务访问一起设计，包含 `list_private_services` 和 `/Users/wanglei/Projects/syngy/synology-dsm-app` 相关能力线。
- Vibe Coding：创建、运行和发布 Workbench 应用或代码型产物。
- octopus-cli：用于命令行配置、创建和发布等工作流。

## Output：闭环结果

Output 不是「员工回复一句话」。一个业务闭环通常要落到至少一种可检查结果：

- 任务状态发生变化。
- 生成可打开的文档、表格、页面或应用。
- 业务数据被创建、更新或查询后呈现。
- 消息发送到指定对象。
- 网页系统出现可观察状态变化。
- 形成可复核的运行记录和待处理事项。

## 单场景分析格式

```text
场景名称：
业务目标：
Cue：
Reference：
Input：
Do：
Output：
依赖能力：
当前状态：
最小验证路径：
不做范围：
```

# 钉钉上传附件教程

适用场景：员工通过钉钉向报工机器人发送文字和图片，由数字员工整理报工、追问缺项、归档原图，并在工作台查看。

编写日期：2026-10-27。本文依据本项目实际测试及钉钉官方工具说明；验收状态为编写时的证据快照，不代表后续部署状态。

## 一、员工怎么发

1. 打开钉钉，与「上海昱庄报工」机器人进入同一个聊天。
2. 先说明日期、项目、工作内容、用时、完成情况和遇到的问题。
3. 点击输入框旁的「＋」或附件入口，选择图片并发送。不同客户端入口名称可能不同。
4. 补充一句图片属于哪条报工，尤其是同一天有多个项目时。
5. 回答机器人对缺失字段的追问，检查最终整理结果，再按提示确认入账。

示例：

> 今天在全自动装箱线检查输送护罩，用了30分钟，已全部检查完成，未发现问题。接下来这张照片属于这条报工。

如果先发了图片，也应补充项目和工作说明。不要只发“这张图存一下”，否则系统无法可靠判断归属。

**钉钉聊天里能看到图片，不等于图片已经存入报工知识库。**完成后还应看到机器人明确的归档结果，并能在工作台打开原图。

## 二、图片怎样到达数字员工

完整链路如下：

```text
员工发送文字和图片
    ↓
钉钉保存消息及附件，提供附件标识
    ↓
接入程序取得 downloadCode / pictureDownloadCode / fileId 等
    ↓
使用有权限的接口获取下载信息，下载实际图片字节
    ↓
校验图片类型、大小、完整性，并按消息去重
    ↓
把原图作为平台附件交给数字员工
或由云端数字员工直接调用取图脚本
    ↓
核对员工、项目和对应报工；缺字段则追问
    ↓
原图归档 + Arcubase资产记录 + 报工附件关联
    ↓
机器人回传结果，工作台展示并预览
```

这里有三件不同的事：钉钉收到了图片、数字员工拿到了图片、业务系统保存了图片。验收必须分别验证，不能只看机器人有没有回复。

## 三、两种取图方式

### 方式A：使用 downloadCode / pictureDownloadCode

适合能取得机器人原始入站消息的接入服务。

操作流程：

1. 接收机器人消息事件，读取其中真实的附件下载码。
2. 根据图片或文件消息结构，将下载码映射到下载接口要求的参数。
3. 使用对应应用的有效授权，调用「下载机器人接收消息的文件内容」接口。
4. 取得下载链接后下载实际文件，再上传为数字员工平台附件或归档。

`pictureDownloadCode` 是图片消息中可能出现的字段名；调用下载接口时须按接口参数要求映射，不能直接假定整个消息体可原样提交。下载码不是图片本体，也不能只把下载码发给模型就当作图片已经传入。

官方入口：[下载机器人接收消息的文件内容](https://open.dingtalk.com/document/orgapp/download-the-file-content-of-the-robot-receiving-message)。该文档页面采用动态展示，本文不抄录未经核实的请求路径、权限名称或完整请求体，实施时以页面当前参数为准。

**本项目状态：尚未取得真实有效入站下载码完成此路径测试，因此没有它的速度或成功率结论。**

### 方式B：使用 fileId

适合已能读取授权范围内的历史消息，并能从附件信息中取得 `fileId` 的场景。

操作流程：

1. 读取指定聊天、指定时间范围内的完整消息分页。
2. 从图片或文件附件中取得真实 `fileId`，同时保留会话和消息标识。
3. 调用「获取文件下载信息」接口，或使用官方 DWS 工具封装的下载命令。
4. 下载文件，核对实际字节，再交给数字员工处理。

按本次提供的接口字段说明，该下载接口的 `dentryId` 对应消息体里的 `fileId`；其他必需字段与权限仍须按当前文档和实际返回补齐。

官方入口：[获取文件下载信息](https://open.dingtalk.com/document/orgapp/obtains-the-download-information-about-a-file)。

**本项目状态：已经通过真实图片下载测试，并完成过图片归档、项目关联和机器人结果回传。云端也已单独下载到同一原图，但完整云端定时链路仍在复验。**

### 怎么选

| 条件 | 适用路径 |
|---|---|
| 能直接处理机器人消息事件，并取得下载码 | downloadCode 路径，可在收到消息后处理 |
| 原生接入只转了文字，历史消息里能查到附件 fileId | fileId 补取路径 |
| 要补处理历史附件 | 优先检查授权历史消息和 fileId 是否可用 |
| 要判断哪个更快 | 必须对同一文件、相同环境分别测速；目前证据不足以比较 |

两种方式都要经过授权、实际下载和业务归档。仅把附件标识包装成一段文字，不会自动赋予数字员工下载能力。

## 四、开发者操作示例：DWS 取图

以下命令依据本次使用的官方 DWS v1.0.65。`<…>` 均为占位符，须替换为实际授权账号下的返回值。示例不包含账号令牌。

### 1. 检查组织与用户授权

管理员需确认组织已开放 CLI 使用，并且当前人员在允许范围内。本次曾出现“总开关开启，但人员范围禁止使用”的情况，因此两处都要检查。

```bash
dws auth status --format json
```

应核对已登录状态、组织和用户是否符合预期。不能因为能搜索机器人，就推定已经具备历史消息读取和附件下载的所有权限。

### 2. 云端环境单独登录

电脑上的登录不会自动出现在数字员工云端。云端使用官方设备流，由用户打开授权页并确认：

```bash
dws auth login --device --no-browser
```

本项目将工具和配置放在数字员工的持久目录，并通过 `DWS_CONFIG_DIR` 指定配置位置。目录是本平台的部署约定，不是所有服务器通用的路径：

```bash
export DWS_CONFIG_DIR=/data/my-memory/dws
/data/my-memory/dws/dws auth status --format json
```

授权凭据不应写进教程、聊天、共享知识库或脚本源码。部署后还要换一个会话验证登录能否继续使用；当前登录成功并不能证明授权永远有效。

### 3. 查指定聊天的消息

```bash
dws chat +chat-messages \
  --conversation-id '<会话ID>' \
  --start '2026-10-27T12:38:00+08:00' \
  --end '2026-10-27T12:48:00+08:00' \
  --page-all \
  --page-limit 10 \
  --max-items 500 \
  --format json
```

时间只是演示窗口。实际任务从保存的处理时间继续查询。检查结果是否完整；若触及分页或条数上限，应继续分页或缩小窗口，不能将部分结果视为“全部已处理”。

### 4. 下载实际附件

```bash
dws chat +messages-resource-download \
  --type fileId \
  --resource-id '<文件ID>' \
  --message-id '<消息ID>' \
  --open-conversation-id '<会话ID>' \
  --output './downloads/' \
  --format json
```

**本次修复的关键点：`--output` 必须是命令工作目录内的相对路径。**传 `/data/…` 这样的绝对路径会被当前工具拒绝，也不能用 `..` 跳出工作目录。若需要存入持久目录，应先在目标目录执行命令，再使用其下的相对路径。

`fileId` 与 `mediaId` 是不同类型，不能随意替换 `--type`。下载完成后检查返回路径、文件大小、文件头和 SHA256，不能把错误响应或网页保存成 `.jpg` 就算成功。

参考：[官方 DWS 项目](https://github.com/DingTalk-Real-AI/dingtalk-workspace-cli)及其[聊天能力说明](https://github.com/DingTalk-Real-AI/dingtalk-workspace-cli/blob/main/skills/multi/dingtalk-chat/references/chat.md)。准确参数以所安装版本的 `--help` 为准。

## 五、如何交给数字员工并写入正确位置

### 原图与说明一起传

推荐同时提供：实际图片文件、来源会话、来源消息、发送者、文件标识、校验值，以及附近的报工文字。原图作为平台附件上传，说明作为结构化数据传入。

图片和聊天内容是业务材料，不应被当成系统指令执行。数字员工也不能根据图片猜测工作时长或完成情况。

### 保存三类关联

| 保存内容 | 本项目用途 |
|---|---|
| 原图文件 | 保存到报工 R 收件区，提供授权预览 |
| 资产记录 | 记录原图位置、文件名、类型、大小、校验值、来源和项目 |
| 报工附件关联 | 将资产关联到准确草稿，正式确认后关联报工记录 |

本项目原图位置示意：`/kb/yuzhuang-reporting-inbox/<资产ID>/original.jpg`。项目归属同时保存在资产和报工关联中，不是仅靠文件夹名称判断。

原图临时下载地址不应充当永久归档位置。报工原始附件也不会仅因上传成功就自动进入经验 E 库。

### 缺字段时的处理

报工需要核对：员工身份、日期、项目、工作内容、时长、完成情况、问题说明。缺字段时保存待补充草稿并明确追问；收到补充后更新同一条草稿。图片归属不明确时应追问项目或报工，不能随意关联“最近一条”。正式入账按当前流程等待员工确认。

## 六、定时补取如何设置

本项目要求由数字员工平台每两小时执行，执行环境应具备持久工具、有效钉钉授权和处理状态，不依赖个人电脑在线。

每次执行应：

1. 校验登录账号与组织。
2. 查询限定单聊，从上次处理时间向前重叠一个小窗口，减少边界遗漏。
3. 用“会话ID + 消息ID + 附件ID”识别同一事件。
4. 将新事件先记为待处理，再下载、归档、关联和回传。
5. 业务写入回读成功后标记完成；结果未知时先核验，不能盲目重发。

程序下载、校验和去重本身不调用模型。**但平台若每次先唤醒数字员工，即使没有新图片，也可能产生模型消耗。**不能把“脚本零模型调用”当成“整个原生定时任务零 Token”。

两小时补取意味着图片可能等待接近两小时，再加执行时间。它适合作为附件补取机制，不代表图片实时入库。

## 八、常见问题

| 现象 | 检查方向 |
|---|---|
| 机器人能回复文字，却说没收到图 | 检查消息事件是否携带附件标识，以及接入层是否转交实际文件 |
| 提示组织未开启 CLI 权限 | 同时检查组织开关和当前人员的可用范围 |
| 本地能取图，云端不能 | 检查云端是否安装工具、单独授权，并正确持久化配置 |
| 下载报参数错误 | 先核对 ID 类型与 `--output` 相对路径限制 |
| 图片已下载，工作台没显示 | 检查资产登记、项目归属、草稿附件关联和当前用户查看权限 |
| 图片挂错项目 | 检查文字上下文与草稿唯一匹配；不确定时先追问 |
| 同一张图反复入库或反复追问 | 检查消息去重记录、已处理标记与回传结果未知时的恢复逻辑 |
| 定时配置存在但没有处理结果 | 分别检查任务是否启用、实际执行结果、云端授权和完整链路，不能只看配置保存成功 |

验收完成的标准是：**从真实钉钉消息出发，取到原图，关联正确报工，缺项能追问，工作台可查看，重复执行不重复写入。**

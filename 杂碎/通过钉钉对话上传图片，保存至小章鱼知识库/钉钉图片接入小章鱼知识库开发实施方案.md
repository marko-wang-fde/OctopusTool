# 钉钉图片接入小章鱼知识库开发实施方案

版本：1.0｜日期：2026-10-27｜案例：昱庄钉钉报工项目

交付对象：接入开发、数字员工配置、Arcubase开发、Workbench前端及测试人员。

本文定义可以直接拆解执行的开发合同，不代表其中所有生产加固项已经部署。标记“现有实现”的部分有本项目代码或测试证据；标记“开发要求”的部分是交付时必须实现的约束。项目仍在其他会话推进，本文不操作现役系统，不以本地文件名称中的“final”推断线上启用状态。

## 1. 目标与交付边界

实现以下用户流程：

> 用户在钉钉机器人聊天中发送图片及说明 → 系统取得真实原图 → 数字员工识别归属、必要时追问 → 原图存入小章鱼知识库 → Arcubase登记可查询元数据 → 工作台按权限查看原图。

最低交付范围：PNG、JPEG、WebP，单张不超过10MB；大小是本项目限制，并非宣称钉钉统一限制。先覆盖一个明确授权的组织、用户与机器人单聊，再扩展多人。

不包含：视频、语音、PDF自动解析；从图片推断工时；自动将原始图片升级为经验知识；未经确认的正式报工入账。

“存入知识库”的本期定义是**原图持久保存、拥有稳定逻辑路径、受权限控制且能够读取/预览**。OCR、全文索引、向量检索是独立可选阶段，不能以“文件上传成功”替代“知识问答可检索到”。

验收成功需同时满足：原图存在且校验一致、资产登记成功、项目/业务关联正确或明确待分类、用户得到准确回执、工作台可见、重复执行不产生重复有效资产。

## 2. 方案选择

### 2.1 本期主路径：数字员工云端DWS补取

沿用本项目已经实际使用的路径：

```text
钉钉消息与附件
  → 官方DWS：限定会话的消息查询
  → 取得fileId并下载原图
  → 确定性脚本：身份校验、文件校验、去重、状态记录
  → 数字员工：项目匹配、说明整理、缺项追问
  → 小章鱼知识库：原图与manifest
  → Arcubase：资产与业务关联
  → 钉钉回执 + Workbench授权预览
```

执行器放在数字员工平台云端。每两小时通过平台原生任务唤醒同一个专用处理会话；不用个人电脑的launchd、cron或Codex定时替代。

这是补取机制，图片可等待接近两小时再加执行时间，不承诺实时到账。文字报工仍可由现有钉钉站点即时处理。

### 2.2 可选后续路径：事件驱动下载码

若团队能开发机器人Stream/回调接收端，可从真实消息事件获取 `downloadCode` 或 `pictureDownloadCode`，调用钉钉官方文件下载接口，再进入相同的归档管线。

该路径须额外实现并验证：官方事件接入、来源验证、事件重放处理、应用授权、下载码参数映射、重试与回执。本项目没有真实下载码验收，**本期不依赖这条路径**。不要让两条路径各自建一份资产；接入第二路径前先统一源消息事件标识。

官方说明入口：[下载机器人接收消息的文件内容](https://open.dingtalk.com/document/orgapp/download-the-file-content-of-the-robot-receiving-message)、[获取文件下载信息](https://open.dingtalk.com/document/orgapp/obtains-the-download-information-about-a-file)。下载码接口页面动态展示，本文不编造未读取到的HTTP参数。采用DWS路径可按第6节已核对命令开发；若实现下载码适配器，必须补充官方当前请求/响应样例及真实测试。

## 3. 小章鱼开发规范：必须遵守的约束

以下依据当前安装的 `workbench-app-development` 技能及其Octopus、命令、Arcubase和本地验收规范。

### 3.1 客户端与身份

1. 新建Workbench使用官方React脚手架，保留 `@syngy/workbench-auth`。现有应用不得重新脚手架覆盖。
2. 本方案需要 `octopus,arcubase`；只要需要任务/项目工作流才另选 `taskboard`，不要因字段名含project就自动增加依赖。
3. 前端通过已有 `createSyngyClients()` facade取得官方客户端，不另建token存储或独立登录页。
4. Host的文件、会话和定时操作使用 `octopus.api`；持久业务表使用生成的Arcubase类型化ingress，不改用Host通用数据库代理。
5. 在团队资源查询前及每次外部写入前执行 `octopus-cli auth whoami --json`，核对profile、host、账号、team。运行时任务另外校验其实际DWS身份和小章鱼业务身份，不能用开发者CLI登录代替。
6. API方法以部署时安装包的 `.d.ts` 为准，不根据相似名称猜参数；包版本升级后先编译与验收。

### 3.2 数据、权限和发布

- 先明确复用哪个Arcubase App；新App需先确定表、字段及权限，再创建并生成SDK。名称相同不能替代ID核对。
- `report_assets_self`、`report_asset_links_self` 在本项目生成代码中仅有读取方法；不得假设员工视图可以写。新增专用写入口时必须在服务端限制本人、组织、项目范围，重新生成SDK。
- 原生数字员工使用其已加载的 `arcubase-cli` 业务工具及当前身份；它不是shell程序，不能照抄网页ingress的 `policy_id` 参数。
- datetime类型写入按规范转换为整数epoch秒并回读验证。若现有字段实际是文本，可保存ISO文本；必须先查schema，不能仅根据字段名或生成的string类型判断。不要把现有脚本里的ISO值直接用于新建datetime字段。
- 本地Workbench需走官方登录/JCode，证明真实后端数据能渲染；禁止用静态示例替代集成验收。
- 发布前完成本地验收并取得开发者发布批准或明确豁免；使用官方 `coding projects publish/watch`。上传原图可使用官方SDK返回的预签名URL，这是文件上传协议，不是替代应用发布渠道。

## 5. 模块划分及输入输出合同

建议实现以下模块。名称是本方案内部模块名，不是平台已经提供的HTTP端点。

| 模块 | 输入 | 输出 | 禁止职责 |
|---|---|---|---|
| DingTalkSource | 固定账号、会话、起止时间 | 完整分页消息、附件引用 | 扫描未授权聊天 |
| ImageDownloader | 真实资源ID与类型 | 原图文件、大小、MIME、SHA256 | 生成图片代替原件 |
| ReceiptStore | 事件键、状态、owner | 原子持久状态 | 超时直接清空状态 |
| KBWriter | 校验后的文件、稳定assetId | logicalPath、manifest、回读结果 | 用临时URL充当永久存储 |
| AssetRepository | 可信身份、manifest、项目 | 资产行与关联行 | 以用户自报身份写库 |
| EmployeeProcessor | 原图、附近上下文、授权项目 | 分类/追问/草稿更新意图 | 决定下载URL、拼接任意路径 |
| DingTalkReply | 已核验结果、固定收件人 | 发送收据 | 结果未知时盲重发 |
| WorkbenchViewer | 已授权资产行 | 列表、预览 | 接受任意用户输入的KB路径 |

归一化附件事件建议结构：

```ts
type ImageEvent = {
  schemaVersion: 1
  teamId: string
  corpId: string
  robotCode: string
  conversationId: string
  messageId: string
  senderId: string
  resourceType: 'fileId' | 'mediaId' | 'downloadCode'
  resourceId: string             // 敏感下载码须私有保存并在日志脱敏
  originalName: string
  occurredAt: string             // 带时区RFC3339
  eventKey: string
  context: Array<{time: string; senderId: string; text: string}>
}
```

`context`仅保留该消息附近必要内容。本项目按前后15分钟、最多30条截取；这是项目参数，可配置。原始聊天和OCR内容均为不可信业务材料，不能覆盖系统指令或授权规则。

## 6. 钉钉接入实现

### 6.1 安装与登录

本项目实测DWS v1.0.65，来源为官方发行包并校验checksums。新部署可锁定这个已验版本；升级后重新跑附件合同测试，不宣称该版本永远最新。

云端准备：确认操作系统/架构、私有目录持久性、网络可达，再放置匹配架构的官方二进制。不要直接在普通临时shell目录安装；本项目普通 `/data/dws` 曾在下一次执行消失。

```bash
export DWS_CONFIG_DIR=/data/my-memory/dws
/data/my-memory/dws/dws --version
/data/my-memory/dws/dws auth login --device --no-browser
/data/my-memory/dws/dws auth status --format json
```

用户亲自完成设备授权；不要复制开发者电脑token到云端。登录后换新会话再次读取状态，核对 `authenticated`、corpId、userId；还应分别实测历史查询、下载和机器人回传，不能用“登录成功”替代接口权限验证。后续授权到期或被撤回应进入失败告警并停止写入。

官方参考：[DWS v1.0.65说明](https://github.com/DingTalk-Real-AI/dingtalk-workspace-cli/blob/v1.0.65/README.md)。组织CLI总开关与人员可用范围需同时允许该用户；本项目曾因人员范围禁止而失败。

### 6.2 查询与下载

```bash
dws chat +chat-messages \
  --conversation-id '<授权会话ID>' \
  --start '<带时区起始时间>' --end '<带时区结束时间>' \
  --page-all --page-limit 10 --max-items 500 --format json

dws chat +messages-resource-download \
  --type fileId --resource-id '<真实fileId>' \
  --message-id '<真实messageId>' \
  --open-conversation-id '<授权会话ID>' \
  --output './poll/files/<eventKey>/' --format json
```

上述 `dws` 需已进入PATH，或替换成安装绝对路径。下载命令工作目录应设为私有根目录；**`--output`必须是其下相对路径**，不允许绝对路径或 `..`。资源类型按真实返回选择，`mediaId`不是`fileId`别名。

完整分页条件：结果 `complete=true`，无partial、failedCount、hasMore。超出上限则缩小时间窗口/继续分页，未完整读取不得推进查询水位。

源消息只能在匹配corp、conversation、sender后进入队列。验证文件头与MIME、0＜大小≤10MB、SHA256；生产实现还应通过图像解码器验证像素和解码资源上限，防止仅扩展名或文件头校验漏掉损坏/超大解码图片。后者是开发要求，不能把现有magic-byte检查称为完整解码验证。

## 7. 幂等、并发和恢复状态

### 7.1 稳定业务键

现有单账号脚本：

```text
eventKey = SHA256(conversationId + "\n" + messageId + "\n" + resourceId)
assetId  = "dingtalk-" + eventKey
```

扩展多租户时，在规范化序列中加入teamId、corpId与资源类型，并使用版本化键格式。升级已有键必须迁移映射，不能直接换算法导致旧图重入库。不同消息重复发相同文件是不同事件；文件SHA相同不等于业务归属相同。

不要按本次数字员工会话ID生成钉钉补取资产ID。本项目旧的 `native_image_archive.py` 适合当前会话直接上传，却用“当前会话+文件哈希”构造ID，不适合作为跨会话补取的唯一键；补取应使用 `cloud_image_poll.py --archive-key` 的源事件稳定ID。

### 7.2 状态合同

推荐逻辑阶段：

```text
DISCOVERED → DOWNLOADED → FILE_STORED → ASSET_REGISTERED
           → LINKED 或 NEEDS_METADATA → REPLY_ACCEPTED → COMPLETED
```

现有脚本顶层是 `discovered/staged/completed`，另用 `archive`、`replyDelivery`记录子阶段。实现者应保留这些子阶段或做明确迁移，不能只靠聊天回复判断已完成。

查询水位和业务完成水位必须分开：完整查询后，先将全部发现事件持久化，再推进查询cursor；下载或写库失败仍保留待处理事件。分页不完整时两者都不推进。

现有 `flock` 仅覆盖一次脚本调用，不能覆盖模型思考与数据库写入整段。因此同时使用：固定专用会话串行调度、事件owner占用、稳定assetId、写前查重与写后回读。多实例部署还需要服务端原子占用/唯一约束；当前文件锁不能充当分布式锁。

### 7.3 中断恢复矩阵

| 中断位置 | 下一次动作 |
|---|---|
| 下载前/下载失败 | 保留DISCOVERED，从同一真实资源重新下载 |
| 原图已存，资产未写 | 校验既有文件并补资产登记，不生成新assetId |
| 资产写请求超时 | 按稳定assetId查真实结果，未核实不得再次create |
| 资产有、关联无 | 仅补关联，不重复建资产或草稿 |
| 项目未知 | 保留NEEDS_METADATA并追问，不猜项目 |
| 回传请求超时 | 保留submission_unknown，核对钉钉收据/消息后再决定，不盲重发 |
| owner属于另一会话 | 不抢占；确认旧执行结束后由受控恢复流程处理 |
| 归档文件与SHA不一致 | 标记冲突并停止，禁止覆盖原件 |

现有 `--ack` 命令本身不证明数据库关联正确，也不会自动证明已回传；调用方必须先完成资产/关联/回执验证。正式加固应把这些证明校验下沉到确定性提交函数，避免仅靠提示词约束。

## 8. 小章鱼知识库写入合同

### 8.1 原生数字员工挂载目录方式

仅在平台确实给该员工授予对应KB目录写权限时使用：

```text
运行时物理路径：/data/kb/yuzhuang-reporting-inbox/<assetId>/original.jpg
业务逻辑路径：  /kb/yuzhuang-reporting-inbox/<assetId>/original.jpg
索引清单：      /kb/yuzhuang-reporting-inbox/<assetId>/manifest.json
```

文件新建使用独占写；已存在时比较SHA，相同则复用，不同停止。写入后重新读取原件计算SHA。目录和文件名由受控assetId与识别出的后缀生成，不拼接用户提供的路径。

manifest最低内容：

```json
{
  "schema_version": 1,
  "asset_id": "dingtalk-<eventKey>",
  "logical_path": "/kb/yuzhuang-reporting-inbox/dingtalk-<eventKey>/original.jpg",
  "file_name": "现场照片.jpg",
  "mime_type": "image/jpeg",
  "size_bytes": 36918,
  "sha256": "<实际SHA256>",
  "channel_message_id": "<钉钉消息ID>",
  "source_conversation": "<钉钉会话ID>",
  "library_id": "R",
  "classification_status": "needs_metadata",
  "uploaded_at": "<实际归档时间RFC3339>"
}
```

只写R原件收件区；现有原件目录可只读。业务归属保存在元数据及关联中，不强制移动图片到项目文件夹。修改分类时更新有版本的元数据，不改原图。

### 8.2 无挂载目录时：官方Host文件API

Workbench/受支持集成执行环境可采用官方上传协议，下面使用本项目当前SDK已存在的方法：

```ts
const api = createSyngyClients().octopus.api
const grant = await api.v1TeamsFilesPresignPutCreate(teamId, {
  rootKind: 'kb',
  key: `yuzhuang-reporting-inbox/${assetId}/original.jpg`
})
if (!grant.url || !grant.finalizeToken) throw new Error('Incomplete upload grant')
const uploaded = await fetch(grant.url, {
  method: grant.method || 'PUT',
  body: imageBlob
})
if (!uploaded.ok) throw new Error('Upload failed')
const file = await api.v1TeamsFilesUploadFinalizeCreate(teamId, {
  rootKind: 'kb', finalizeToken: grant.finalizeToken
})
if (!file.logicalPath || file.sizeBytes !== imageBlob.size) {
  throw new Error('Finalize mismatch')
}
// 接下来上传manifest、通过授权读取校验SHA，再登记资产；不是到此即业务成功。
```

这段是已具备官方Workbench身份上下文内的代码骨架。独立后台不可直接调用浏览器facade，必须使用平台支持的服务身份适配器，不从浏览器复制token。不得自行构造OSS地址或绕过finalize。

## 9. Arcubase表与身份映射

### 9.1 资产表 `report_assets`

| 字段 | 约束/来源 |
|---|---|
| asset_id | 稳定事件资产键；写前查重，写后回读 |
| org_id / library_id | 受控teamId / 固定R |
| uploader_id | 可信身份映射得出的内部用户ID |
| channel_message_id | 原始钉钉消息ID，不能填内部补取会话消息ID |
| logical_path | 归档返回的稳定KB路径 |
| file_name / mime_type / size_bytes / sha256 | 实际原件校验结果 |
| width / height | 若已解码则保存，不填猜测值 |
| uploaded_at / business_date | 归档时间 / 用户明确业务日期，二者不能混淆 |
| project_ref | 授权项目目录唯一匹配，否则空 |
| ingest_status | stored仅在原件和登记校验通过后使用 |
| classification_status | needs_metadata或classified |
| description_confirmed | 用户明确说明 |
| description_ai / ocr_text_unverified | AI推断与OCR，不能冒充用户确认 |
| revision / dataset_mode | 初始1 / 演示与正式明确区分 |

### 9.2 可选业务关联表 `report_asset_links`

业务需要挂到报工时使用：`link_id`、`asset_id`、`draft_id`、`worklog_id`、`project_ref`、`link_reason`、`confirmed_by`、`created_at`、`status`。

推荐沿用本项目 `link_id = native:<draft_id>:<asset_id>`；这些字段存业务键，不存Arcubase数字rowId。未正式确认的草稿关联为pending；报工确认后更新同一关联为effective。单纯图片归档不得触发新增工时。

### 9.3 权限规则

- 钉钉senderId、staffId、平台userId、Arcubase原生用户ID分别保存，显式映射，不混用。
- 核对当前数字员工调用身份，再读取唯一有效映射。未知用户拒绝业务写入并提示绑定，不临时换管理员身份。
- 普通员工只能查看本人且授权项目范围内的资产；PM限本人管理项目；管理员管理范围由服务端规则明确。
- 数据表读权限和KB文件权限都要满足，不能只在前端隐藏按钮。
- 本期单聊轮询用本人OAuth；扩展全员前先验证其合法会话覆盖范围及隔离，不能假设一个人的OAuth能读取所有员工消息。

原生CLI在本项目曾出现“row get有结果、文本filter查询为空”的兼容问题。临时处理是在当前账号已授权返回中完整分页后严格匹配；上限10000行，超过则停止判重。新实现优先修复/验证查询合同，不能把这个临时做法扩展为全库无权限扫描。

## 10. 数字员工执行协议

先做确定性步骤，再让模型判断业务语义：

1. 脚本查询并下载，返回pending事件及当前会话原图路径。
2. 核验身份、可访问项目、资产和关联；遇到错误不能解释为“没有图片”。
3. 同一源事件已有正确资产及关联时复用并完成收据，不重复归档/追问。
4. 新图用稳定assetId归档，登记资产并回读。
5. 仅当用户明确说明且日期、项目、内容、时长唯一匹配时关联原草稿；保留原 `draft_id` 和钉钉聊天来源。
6. 字段缺失保存待补充草稿，只追问缺项。单独上传图片不强迫用户填完整报工表，先问资料归属即可。
7. 最终中文回执说明已保存/待分类、项目、需要补充的信息。只有真实保存后才能说“已保存”。
8. 机器人发送成功并验证后才结束该事件；未知发送结果保持待核对。

现有脚本操作接口：

```bash
python3 /data/my-memory/dws/cloud_image_poll.py --start '<首次起点>' --end '<测试终点>'
python3 /data/my-memory/dws/cloud_image_poll.py
python3 /data/my-memory/dws/cloud_image_poll.py --archive-key '<eventKey>'
python3 /data/my-memory/dws/cloud_image_poll.py --reply-key '<eventKey>' --reply-text '<核验后的中文回执>'
python3 /data/my-memory/dws/cloud_image_poll.py --ack '<eventKey>' --asset-id '<已核验assetId>'
```

这些调用必须从固定原生会话工作目录执行。运行脚本的数字员工须能访问私有工具目录及目标KB根目录。未知结果不删除state、锁文件或旧资产来强行重跑。

## 11. 工作台展示与知识检索

### 11.1 原图预览

列表通过生成的资产ingress读取，按实际权限选择入口。仅展示有效stored资产，已排除的重复测试行不能计数。界面显示项目、业务日期、员工说明、待分类状态及原图入口。

预览必须先按权限读取资产行，再对允许的KB根目录创建临时预览会话：

```ts
const asset = await authorizedAssetIngress.get(rowId)
const path = asset.fields.logical_path
if (!path?.startsWith('/kb/yuzhuang-reporting-inbox/')) {
  throw new Error('Path outside configured library')
}
const preview = await createSyngyClients().octopus.api
  .v1TeamsFilePreviewSessionsCreate(teamId, {logicalPath: path, sourceKind: 'kb'})
if (!preview.assetUrl) throw new Error('Preview unavailable')
// 临时用于显示；不把assetUrl存回资产logical_path。
```

兼容旧R目录时增加受控白名单；同时依赖平台路径规范化和后端授权，前端字符串检查不能单独构成安全边界。403显示权限不足，404显示原件待修复，不伪装为空列表。

### 11.2 如需“知识库问答能找到图片”

另建可追溯的文字旁注，记录assetId、项目、业务日期、确认说明及明确标为未核实的OCR；使用平台支持的知识库绑定/同步配置将目标目录纳入检索。知识索引API与状态在本次文件归档路径中未验证，开发前需从当前CLI/SDK取得真实合同，不能自行发明接口。

检索验收必须用一段唯一文本实际提问，并返回正确资产关联与授权预览。没有完成此测试，只交付“文件归档可查看”，不能承诺语义检索已上线。

## 12. 原生定时任务配置

使用数字员工平台的 `configure schedule trigger`，不使用Codex自动化。

```json
{
  "subject": "钉钉图片补取归档",
  "actionType": "append_to_conversation",
  "cronSpec": "0 */2 * * *",
  "timezone": "Asia/Shanghai",
  "enabled": false,
  "targetConversationId": "<专用处理会话ID>",
  "promptText": "执行本方案第10节协议。先运行云端取图脚本；只处理授权单聊。无pending不发例行消息；任何失败按真实阶段记录。使用稳定事件资产键，保持同一草稿，回读后回传，确认发送结果后ACK。禁止重置状态、扩大账号范围或写经验E库。"
}
```

完整业务约束应放到员工持久规则文件并在prompt中引用，不能只依赖这一段摘要。先列表查重，存在则原位更新：

```bash
octopus-cli configure schedule trigger list --json
octopus-cli configure schedule trigger add --body-file schedule.json --json
octopus-cli configure schedule trigger disable <triggerId> --json
octopus-cli configure schedule trigger show <triggerId> --json
octopus-cli configure schedule trigger run <triggerId> --json
octopus-cli configure schedule trigger runs <triggerId> --json
octopus-cli configure schedule trigger enable <triggerId> --json
```

首次create后必须回读；本项目曾出现请求 `enabled=false` 而创建响应为true，故需要显式disable并回读，不能相信请求值就是实际状态。手动运行是否要求先enable，以当前CLI/API实际响应为准；如需要，使用受控测试窗口并及时核验状态。

验收要同时看触发器run与对应员工turn结果，`running`不等于成功。用户允许不等待自然触发时，手动触发完整同一任务链路、重复运行通过、最终enabled及计划回读正确即可交付，并注明“未等待自然周期”，不要伪造自然触发证据。

没有新图时脚本本身不调用模型，但原生任务先唤醒员工仍有模型成本。OCR/视觉分析只针对新图；不要把整个聊天历史反复放入模型上下文。

# Octopus W+E 项目开发方法论

> 版本：1.0  
> 适用对象：FDE、产品经理、Workbench 前端开发、ArcuBase 建模及平台配置人员  
> 适用范围：Octopus、数字员工、ArcuBase、Workbench、知识库、文件、消息、计划任务及外部系统  
> W = Workbench，E = Digital Employee

## 1. 核心思想

Octopus W+E 项目不是“做一个页面，再加一个机器人”，而是把真实业务重新分配给人、数字员工、结构化数据和平台能力。

一个可交付项目必须回答六个问题：

1. 要解决的真实业务问题是什么？
2. 人、数字员工和系统分别负责什么？
3. 哪些是业务数据，哪些是知识，哪些是平台能力？
4. 每个角色能看什么、能做什么、不能做什么？
5. 用户如何在 Workbench 中低负担地完成日常工作？
6. 如何用真实账号、真实数据和完整链路证明系统可用？

统一开发主线：

```text
理解业务
→ 概念建模
→ 用例与约束
→ 站点地图
→ 资源映射
→ ArcuBase 数据与权限契约
→ SDK Codegen
→ Workbench 与数字员工实现
→ 真机验收
→ 人工批准发布
→ 运行反馈与复盘
```

最重要的顺序原则：**业务先于表，表先于 SDK，SDK 先于页面，本地验收先于发布。**

## 2. 立项判断

### 2.1 适合 W+E 的项目

- 多角色围绕同一批业务对象持续协作。
- 业务对象有状态、负责人、时间、附件和审计要求。
- 用户需要列表、筛选、表单、审批、操作和统计，单靠对话效率低。
- 数字员工需要处理文档、理解语义、生成摘要、做判断或跨系统执行。
- 业务过程需要留痕、查询、巡检、提醒和度量。

### 2.2 不宜直接开发 Workbench 的项目

- 只需要一次性报告、临时页面或单次活动。
- 业务对象、主流程和责任边界尚未明确。
- 已有成熟系统，只需要低频查询或录入，可先用 Browser/WebSkill 试点。
- 数据没有稳定来源、没有权限路径或尚未获得客户授权。
- 只需要知识问答，不需要结构化业务闭环。

### 2.3 立项决策卡

| 项目项 | 必须明确的内容 |
| --- | --- |
| 业务目标 | 解决什么问题，对什么经营指标产生影响 |
| 主要用户 | 谁操作、谁审批、谁查看、谁管理平台 |
| 核心对象 | 需要持续管理的人、单、事、资源 |
| 主流程 | 从什么事件开始，到什么业务结果结束 |
| 数字员工价值 | 哪些环节需要语义理解、生成、判断或主动执行 |
| 交付端 | Workbench、企微、邮件、对话、报表或外部系统 |
| 本期范围 | 做什么，以及明确不做什么 |
| 成功标准 | 哪条端到端业务链跑通才算完成 |

## 3. 需求建模：五层模型

### 3.1 概念 Concept

先统一业务语言，再开发系统。至少定义：

- 角色：操作者、审批者、管理者、外部协作者、数字员工。
- 对象：单据、人员、客户、任务、文件、资源、规则、消息。
- 关系：主从、归属、引用、多对多、快照、历史版本。
- 状态：初始、进行、暂停、成功、失败、取消、关闭和恢复。
- 终态：什么情况算完成，什么情况算业务关闭。

产物：名词表、角色表、对象关系树、状态机。

### 3.2 用例 Use Case

每个用例必须说明：

```text
谁
在什么条件和时间
从什么入口
提供什么输入
执行什么动作
得到什么结果
失败时如何处理
由谁接管
```

用例必须可验证，不能用“智能化、高效处理、自动赋能”代替行为定义。

产物：角色用例表、端到端 happy path、异常与恢复路径。

### 3.3 约束 Constraint

- 可见性：哪些角色不能看哪些数据。
- 动作权限：谁能创建、读取、更新、删除、审批和导出。
- 行级范围：本人、本部门、下级部门、关联数据或全量。
- 字段范围：金额、证件、联系方式等敏感字段。
- 流程规则：哪些阶段不能跳过，暂停后如何恢复。
- 幂等：重试、重发、重复提交如何避免重复数据。
- 审计：哪些动作记录操作人、时间、前后值和原因。
- 人工门禁：邮件、付款、合同、批量变更等是否必须确认。

产物：权限矩阵、业务红线、幂等、审计和保留规则。

### 3.4 站点地图 Sitemap

先决定业务在哪个端发生：

- Workbench：复杂列表、表单、审批、流程和分析。
- 对话/企微：文件投递、简短指令、提醒、回执和问答。
- 邮件：正式对外通知。
- 计划任务：按时间或业务状态主动触发。
- 外部系统：通过 API、浏览器或设备执行。

Workbench 需要明确导航、路由、角色、数据源、主操作、深链和登录回跳。

产物：菜单树、路由表、页面—角色—数据源对照表。

### 3.5 资源映射 Resource Mapping

| 对象或能力 | 推荐资源 |
| --- | --- |
| 持续查询、更新、统计的业务记录 | ArcuBase |
| 用户、团队、角色、部门和成员 | Octopus 平台组织与身份 |
| 制度、规则、手册、口径、FAQ | Knowledge Base |
| 原始文件与附件 | File Gateway/KB，ArcuBase 保存指针和元数据 |
| 文档理解、生成、语义判断 | 数字员工 |
| 超时巡检与定期提醒 | 计划任务 |
| 可认领、分派、跟踪的工作 | Taskboard |
| 无 API 的网页系统 | Browser/WebSkill + 设备 + Secret |
| 平台不能承载的重事务或特殊算法 | 独立后端 |

## 4. 资源分流与调用原则

### 4.1 A/B/C 三档

| 档位 | 定义 | 载体 |
| --- | --- | --- |
| A：结构化业务数据 | 有状态、负责人、时间、关系、统计和写回要求 | ArcuBase |
| B：平台共享能力 | 身份、组织、知识、文件、消息、调度、数字员工 | Octopus Host API/SDK |
| C：自建能力 | 重事务、特殊算法、专有协议或平台无法承载的服务 | 独立后端/工具 |

优先用 A+B 完成闭环，不为了复刻传统软件架构而无故增加 C。

### 4.2 数据、知识与文件不能混用

- 业务数据是操作对象，进入 ArcuBase。
- 知识是执行依据，进入 KB。
- 文件是原始证据或附件，进入 File Gateway/KB。
- ArcuBase 保存文件指针、hash、文件名、类型、大小和业务关联。

### 4.3 全资源调用表

| 资源 | 调用原则 |
| --- | --- |
| Workbench Auth | 使用官方认证包；禁止自建登录和 token store |
| Host API | 使用认证后的 Workbench fetch 或官方 SDK |
| ArcuBase | 明确 App → schema/access rule → codegen → typed ingress |
| 数字员工 | 最小完整输入、结构化输出、超时、重试、人工接管 |
| KB | 明确目录、同步、可见、读写和检索范围，用样例验证 |
| 文件 | presign-put → PUT → finalize；读取用 presign-get |
| 计划任务 | 触发可追溯、同单同提醒幂等、状态解除后停止 |
| Taskboard | 仅在真正需要任务认领和追踪时使用 |
| 企微/邮件 | 真账号试点；敏感或对外动作保留人工确认 |
| Secret | 只存平台 Secret，不进入 skill、文档、表或对话 |
| Browser/WebSkill | 先试跑；重复稳定后固化；失效时可观察、可重录 |

## 5. ArcuBase 开发方法

### 5.1 明确选择 App

- 复用已有 App：检查 ID、schema、稳定 key、访问策略和现有数据。
- 创建新 App：先确认表、字段、关系和权限设计，再创建。

禁止按名称猜 App ID、静默创建存储，或为了临时通过页面直接改生产 schema。

### 5.2 数据建模

- 一张表对应一个稳定业务对象或必须独立审计的过程记录。
- 字段 key 使用稳定、TypeScript 友好的英文名。
- 状态枚举同时定义允许流转和业务终态。
- 明确主从、历史、快照和当前值的责任。
- datetime 统一写 epoch 秒，首条写入后立即读回校验。
- member 字段存 ArcuBase user ID，明确映射 Host user ID。
- subform 子行使用 fieldId；复杂子表编辑前用行级 `get`。
- schema 变更和批量导入前备份 schema、规则和数据。

### 5.3 权限设计

平台角色是唯一权威源，ArcuBase access rule 是其对数据权限的投影。

每张表明确：

- 角色可执行的 view/add/edit/delete/bulk update/archive。
- 本人、本部门、下级部门或关联对象的行级范围。
- 敏感字段的字段级读写范围。
- 数字员工以什么身份读写。
- 平台管理员是否需要业务数据权限。

无匹配正式入口时默认拒绝，不回退到开发全权。前端隐藏按钮不是权限隔离。

### 5.4 Workbench 与 ArcuBase 权限协同

#### 5.4.1 协同原则：一条身份链，两层职责

Workbench 与 ArcuBase 不是两套互相独立的权限系统，而是一条权限决策链上的不同环节：

```text
Workbench 登录会话 / 当前用户
  → Octopus 平台角色、组织与团队成员关系
  → Host user ID 与 ArcuBase user ID 映射
  → 选择与业务对象、角色、动作匹配的 generated ingress
  → ArcuBase access rule 执行行级条件与字段级权限
  → Workbench 根据 can() 呈现页面、按钮和字段
  → 生成 SDK 发起调用，后端再次执行正式授权
```

职责边界如下：

| 层次 | 负责内容 | 不能代替的内容 |
| --- | --- | --- |
| Octopus / Workbench 会话 | 确认当前用户、团队、平台角色、组织上下文 | 不直接授予某张业务表的数据权限 |
| Workbench 前端 | 路由、菜单、按钮、字段的可见性与可操作性；解释无权原因 | 不能以隐藏元素替代后端鉴权 |
| generated ingress | 封装指定实体的一套完整访问策略、动作、条件和字段权限 | 不能由页面临时拼接或放宽策略 |
| ArcuBase access rule | 对实际请求执行动作、行级和字段级授权 | 不负责页面交互和业务提示 |

前端权限负责体验，后端权限负责安全。两者必须来源一致、表现一致；发生冲突时，以 ArcuBase 的拒绝结果为最终结论。

#### 5.4.2 权限要分四层设计

| 权限层 | 设计问题 | Workbench 表现 | ArcuBase 落点 |
| --- | --- | --- | --- |
| 路由与菜单 | 用户是否应进入该业务域 | 菜单显示、路由守卫、无权页 | 至少存在一个可用的业务 ingress/action |
| 动作权限 | 是否可查看、新增、编辑、删除、归档或批量操作 | 按钮可见、可用和操作提示 | rule actions |
| 行级权限 | 可以操作哪些记录 | 列表范围、详情访问、选择器候选范围 | rule query condition |
| 字段级权限 | 哪些字段可读、可写 | 字段隐藏、脱敏、只读或禁用 | field read/write permissions |

不要只做“角色能不能进入页面”的粗粒度判断。能进入页面，不代表能查看全部记录；能编辑记录，也不代表能改所有字段。

#### 5.4.3 角色到 ingress 的映射

每个 generated ingress 应代表一套可解释、可审计的完整访问策略。建议使用稳定语义命名，例如：

```text
customer_viewer
customer_owner_editor
order_department_manager
platform_admin_exception
digital_employee_order_processor
```

运行时按“实体 + 当前身份/角色 + 所需动作”选择 ingress：

1. 从 Workbench 会话读取当前用户、平台角色和组织上下文。
2. 将 Host user ID 映射为 ArcuBase user ID；member 字段和按本人过滤使用后者。
3. 找到与实体、身份和动作匹配的正式 ingress。
4. 先用该 ingress 的 `can()` 判断页面交互，再通过同一个 ingress 的 SDK 方法执行请求。
5. 没有匹配项时默认拒绝，禁止回退到开发入口、全量入口或管理员入口。

同一用户有多个角色时，可以合并其合法能力，但每个动作仍应使用满足该动作的最小权限 ingress。不要为了省事选择范围最宽的入口。不同角色的行级条件或字段权限不同时，应拆成不同 access rule/ingress。

#### 5.4.4 Workbench 的权限呈现

前端尽量根据生成 SDK 暴露的能力判断，而不是在页面中复制一套角色名称列表：

```ts
const canView = ingress.can('view')
const canCreate = ingress.can('create')
const canEditOwner = ingress.can('update', { field: 'owner' })
const canReadAmount = ingress.can('view', { field: 'amount' })
```

具体 API 以当前 codegen 产物为准。页面至少遵守以下规则：

- 菜单与路由：用户没有任何该业务域的可用动作时，不显示入口；直接访问路由仍需守卫。
- 列表与详情：只展示后端返回的授权记录，不在前端先拉全量数据再过滤。
- 操作按钮：用 `can()` 控制可见性或可用性，并给出清楚的无权原因。
- 表单字段：无读权限时不请求、不渲染；有读无写权限时只读展示；有写权限时才允许提交。
- 后端拒绝：保留真实错误语义，不把 403/无权限静默显示成“暂无数据”。
- 真实空状态：只有请求成功且结果为空时，才显示业务空状态。

#### 5.4.5 身份映射与本人数据

Workbench 会话中的用户 ID 通常是 Host user ID，ArcuBase 的 member 字段需要 ArcuBase user ID。两者必须通过正式用户绑定关系映射，不能把一个 ID 直接当成另一个使用。

建议在启动或首次业务请求时完成身份解析，并保留：

```text
hostUserId
arcubaseUserId
teamId
roleIds / actorIds
organizationContext
```

如果缺少 ArcuBase 绑定：

- 默认阻止依赖 member 字段的新增、认领、转交和“本人数据”查询。
- 页面明确提示“账号尚未绑定业务数据身份”，不能伪装成系统无数据。
- 不自动用姓名、手机号或模糊搜索结果替代正式 ID 映射。

#### 5.4.6 平台管理员与数字员工例外

平台管理员能配置平台，不等于天然拥有全部业务数据。确需业务数据权限时，应建立独立的 `platform_admin_exception` 规则，明确：

- 允许的实体和动作。
- 行级范围与敏感字段边界。
- 使用目的、审批依据和审计要求。
- 是否只在排障或数据修复期间启用。

数字员工也应作为独立业务身份设计：

- 不默认冒用发起人的全部权限。
- 使用专用 actor/role 与 ingress，只获得完成任务所需的最小权限。
- 写入记录同时保留业务发起人和实际执行身份。
- 涉及外发、删除、批量修改或敏感字段时，增加人工确认或审批。

#### 5.4.7 多表操作的权限预检

一次业务操作需要写多张表时，在第一笔写入前检查全部必要权限：

```text
主表 create
+ 明细表 create
+ 关联表 update
+ 审计表 create
= 全部通过后才开始执行
```

若平台当前不提供跨表原子事务，应同时设计：

- 幂等键，避免重试产生重复记录。
- 步骤状态，标识已完成和未完成环节。
- 补偿动作，撤销或修复部分成功的数据。
- 可追踪错误，便于人工接管。

不得出现“主表已成功、明细因权限不足失败”后仍向用户提示整体成功。

#### 5.4.8 权限变更的开发闭环

```text
确认角色—数据权限矩阵
  → 配置平台角色、actor 与组织范围
  → 创建或更新 ArcuBase access rule
  → 重新执行 codegen
  → 更新 ingress 选择、can() 与前端交互
  → 类型检查和构建
  → 正向账号 + 反向账号验证
  → 经批准后发布
```

角色、字段、行级条件或 access rule 变化后，即使旧代码仍能构建，也必须重新生成 SDK 并验证。切换测试身份时重新登录或刷新会话，避免旧 token、旧角色缓存造成误判。

#### 5.4.9 最小验收矩阵

每个业务对象至少维护下表，作为需求、配置、前端和测试共同依据：

| 角色/身份 | 实体 | ingress | 动作 | 行级范围 | 字段范围 | UI 预期 | API 预期 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 业务经办人 | 示例主表 | owner_editor | view/update | 本人负责 | 常规字段可写、审批字段只读 | 可见编辑按钮，审批字段只读 | 仅本人记录可更新 |
| 部门负责人 | 示例主表 | department_manager | view/update | 本部门 | 审批字段可写 | 可见审批入口 | 跨部门请求拒绝 |
| 普通成员 | 示例主表 | viewer | view | 被授权记录 | 敏感字段不可读 | 仅查看，无编辑按钮 | 写请求拒绝 |
| 数字员工 | 示例主表 | de_processor | view/update | 待处理记录 | 仅处理所需字段 | 不适用或展示执行状态 | 越界字段写入拒绝 |

验收必须覆盖：

- 有权账号能看见入口，并完成允许的动作。
- 无权账号看不见入口，直接访问路由仍被拒绝。
- 绕过 UI 直接调用 SDK/API 仍被 ArcuBase 拒绝。
- 行级条件对本人、本部门、跨部门和无关联记录分别生效。
- 敏感字段在列表、详情、导出和接口响应中均符合权限。
- 多角色用户只获得合法能力并集，不意外获得宽泛数据范围。
- 撤销角色或调整组织后，重新登录能立即验证新边界。
- 403/无权限、身份未绑定、真实空数据和系统异常具有不同提示。

#### 5.4.10 交付审计材料

权限交付不只交一组配置，还应同步交付：

- 角色—实体—动作—行级—字段级权限矩阵。
- Workbench 路由、菜单、按钮、字段与 ingress/action 的映射表。
- Host user ID 与 ArcuBase user ID 的绑定与异常处理说明。
- 管理员例外和数字员工专用规则清单。
- 正向、反向账号的验收记录及关键截图/日志。
- access rule、schema 和生成 SDK 的版本或备份位置。

### 5.5 Codegen 是数据边界

- schema 和规则就绪后生成 TypeScript SDK。
- 页面只通过生成的 typed ingress 读写业务数据。
- 页面不手写 policy ID、field ID 或 ArcuBase 请求。
- 使用 `can()` 或等价检查控制入口可见性和可用性。
- 多表操作在首笔写入前检查全部必需权限。
- SDK 生成成功不代表真实数据已经接通。

## 6. 数字员工开发方法

### 6.1 设计卡

| 项 | 内容 |
| --- | --- |
| 名称与身份 | 使用清晰的业务角色名称 |
| 服务对象 | 主用户、次用户和外部协作者 |
| 业务职责 | 有限、可验收的任务 |
| 不做范围 | 不自动做的决策、对外动作和高风险操作 |
| Home 策略 | 按用户、按数字员工或全局共享 |
| 身份与权限 | ArcuBase、KB、消息和任务中的身份范围 |
| 依赖能力 | 已稳定、待试点或不可用 |
| 失败语义 | 记录什么、通知谁、如何人工接管 |

### 6.2 CRIDO 场景

- Cue：什么事件触发。
- Reference：执行依据和知识。
- Input：结构化数据、文件和用户上下文。
- Do：有限、有边界的执行步骤。
- Output：可校验结果、写入位置和通知对象。

每个场景补充能力状态、最小验证路径、超时、重试、幂等和人工接管。

### 6.3 人机职责

数字员工负责：

- 文档理解、摘要和结构化抽取。
- 规则与语义结合的复杂判断。
- 自然语言问答、解释和初稿。
- 授权范围内的消息、计划、文件或外部调用。

程序负责：

- 身份、权限、数据范围和流程前置检查。
- JSON/schema/枚举/ID 约束和完整性校验。
- 超时、取消、有限重试、幂等和审计。
- 通过正式 ingress 写入确认结果。

人负责：

- 定义问题、边界和风险承受度。
- 确认权限、外部沟通、金额、合同和人事决策。
- 接管数据不足、权限不足和外部系统异常。

### 6.4 长任务与 SSE

- 设置超时和 AbortController。
- 区分过程、工具、文本增量和最终完成事件。
- 前端显示阶段、重试、成功和失败，不泄露敏感内容。
- 不把过程帧当最终答案，不把未校验输出直接写库。

## 7. Workbench 工程方法

### 7.1 官方技术栈

```text
React + Vite + TypeScript + Tailwind CSS + shadcn/ui
+ @syngy/workbench-auth
+ @syngy/workbench-devtools
+ @syngy/workbench-arcubase-codegen
+ @syngy/arcubase-client
+ @syngy/octopus-client（需要平台资源时）
```

只使用官方 Workbench React 脚手架和 `octopus-cli coding` 管理生命周期。

| 需求 | Feature |
| --- | --- |
| 仅认证 Workbench UI | 空 |
| 团队、组织、成员、数字员工、对话、文件、知识 | `octopus` |
| 任务或项目 | `taskboard` |
| 持久、共享、可查询的业务数据 | `arcubase` |

### 7.2 Preflight

编码前核对：

1. CLI 版本、profile、Host、账号和 team。
2. 当前账号是否有项目管理权限。
3. ArcuBase App 与 team binding。
4. 数字员工 ID、Home、身份、技能、知识授权和访问策略。
5. 主要路由、实体、读写动作和验收路由。
6. 在仓库记录 route → entity → ingress 和预期行数。

上下文不匹配时停止，不自动切换 profile、team 或 App。

### 7.3 本地开发

- 第一屏直接呈现真实业务面。
- 未登录时由 Workbench DevTools 完成 JCode 登录并回原路由。
- 页面显示 SDK 返回的真实数据或真实空状态。
- 新增和编辑贯通表单、校验、写入、错误、成功和重新查询。
- 本地验证默认只读；测试写入有明确标识和清理策略。

### 7.4 可见功能契约

```text
权限判断
→ 打开表单或操作面
→ 字段和格式校验
→ 业务前置与多表权限预检
→ 正式 SDK/API 调用
→ 加载状态
→ 后端错误可见
→ 成功反馈
→ 重新查询受影响数据
```

未实现的搜索、筛选、同步、新增、保存、导出和通知不得出现在主业务面。

## 8. EUI：企业工作台交互规范

EUI 在本文中指 Enterprise UI：面向持续作业、流程协同、数据判断和责任追溯的企业级界面。

### 8.1 首要原则

- 用户进入页面就知道当前要办什么。
- 按业务流程组织，不按后端表组织。
- 状态、异常、权限和下一步是一等信息。
- 界面不承诺后端未实现的能力。
- 高频任务优先效率和可扫描性。

### 8.2 信息架构

- 左侧导航按业务阶段分组。
- 顶部显示页面、当前用户、部门/角色和切换账号入口。
- 同一业务对象尽量只有一个主入口。
- 通知深链携带业务 ID，登录后回原路由并聚焦对象。

### 8.3 统一页面模式

任务型列表：

```text
标题 + 主操作
待办（数量）/ 办理历史（数量）
筛选与搜索
可扫描列表
统一分页
详情/办理抽屉
```

列表只显示对象、所属、状态、关键时间、负责人和单一详情入口。长描述、历史和复杂操作进入抽屉。

详情抽屉：

```text
基础资料
当前阶段与状态
关联对象和历史
异常、原因或审批意见
底部主操作
```

同意、拒绝、改期、上传、转交等动作在完整上下文中执行，不在表格行堆叠危险按钮。

### 8.4 状态与反馈

- 加载、空、错误和成功是四个独立状态。
- 空状态说明“为什么空 + 下一步怎么做”。
- 后端错误在操作上下文可见。
- 暂时不可操作：禁用并说明原因。
- 永久无权：不展示入口，后端继续拒绝。
- 危险或不可逆操作使用 AlertDialog。
- 长时 AI 任务展示阶段、重试和最终结果。

### 8.5 表单与选择器

- 少量枚举使用 shadcn `Select`。
- 大量可搜索人员、项目、部门使用 `Popover + Command` Combobox。
- 部门保留层级，人员按业务范围过滤。
- 必填、格式、范围和业务前置错误显示在字段附近。
- 重复对象使用结构化可增删条目。
- 按钮文案表达业务结果，如“提交审批”“确认发送”。

### 8.6 视觉与响应式

- 收敛在 shadcn/ui `new-york` 体系。
- 统一圆角、边框、间距、字号、按钮层级和状态色。
- 桌面侧栏常驻，小屏转抽屉导航。
- 宽屏可用主内容+摘要双栏，窄屏降为单栏。
- 小屏表格水平滚动，不通过过度压缩破坏可读性。
- 有 Figma 源文件时优先使用结构信息对齐。

### 8.7 前端红线

1. 无 mock 业务数据、占位页和假进度条。
2. KPI、计数、状态、列表和图表来自真实查询。
3. 不手写未认证 fetch 访问平台或 ArcuBase。
4. UI 角色判断只优化体验，不替代后端权限。
5. 日志和错误不暴露敏感原文、token、签名 URL 和内部策略。

## 9. 迭代与并行策略

只有以下契约冻结后才并行：

- 业务名词与对象边界。
- 主用例、状态流转和业务红线。
- ArcuBase schema、稳定 key 和权限矩阵。
- Workbench 路由与数据映射。
- 数字员工输入、输出和不做范围。

冻结后可以并行：

- ArcuBase schema/access rule 实施与备份。
- Workbench 页面骨架、通用组件和读取适配。
- 数字员工 Skill、对话契约和独立场景试验。
- 测试数据、验收用例和证据模板。

一个迭代应完成一个可验证业务切片：

```text
某角色创建业务对象
→ 写入真实 ArcuBase
→ 待办角色读取
→ 允许与拒绝权限正确
→ 完成处理
→ 列表、状态和历史刷新
```

不要用“完成三个页面样式”作为迭代目标。

## 10. 四层验收

| 层级 | 验收内容 | 不能证明成功的证据 |
| --- | --- | --- |
| 契约层 | schema、access rule、codegen、类型 | 仅看到 SDK 文件 |
| 数据层 | 真实查询、真实空态、写入读回、幂等 | mock、常量、本地 state |
| 操作层 | 表单、写入、错误、成功、刷新 | 截图、静态页、按钮存在 |
| 业务闭环层 | 多角色、多阶段、正反权限、异常恢复、人工接管 | 只验一个页面或 API |

### 10.1 必验项

- 未登录进入官方登录流程，登录后回原路由。
- 页面显示真实用户、团队和角色。
- 每个主页面显示真实记录或真实空态。
- 每个可见主操作到达正式写入通道。
- 后端错误可见，成功后重新查询。
- 允许和禁止角色在 API 层对照验证。
- 敏感字段对无权角色不可读。
- 数字员工输出、超时、重试和接管通过。
- 消息、邮件、深链和计划任务用真账号试验。
- 深层路由直达与刷新不返回 404。
- 移动宽度、导航、表格、抽屉和主操作可用。

### 10.2 验收记录

保留日期、验收人、环境、角色、前置数据、步骤、预期与实际、URL/截图/日志/记录 ID、偏差、接管方式和结论。

## 11. 发布与变更管理

### 11.1 发布门禁

```text
本地真机验收通过
→ 报告本地 URL、资源 ID、数据证据和未解问题
→ 开发负责人显式批准发布
→ 执行项目声明的 test/build
→ 确认 dist/index.html
→ publish
→ watch 部署任务
→ active + workbenchUrl
→ 线上路由、登录、刷新和真实数据复测
```

发布批准是独立门禁，不因早期说过“最终需要上线”而自动豁免。

### 11.2 线上变更前

对 schema、access rule、角色、数字员工、KB 权限和批量数据变更，事前保存：

- profile/host/team 证据。
- 当前资源配置或导出。
- schema、access rule 和可读数据行。
- 变更目标、迁移计划、默认值和排除项。
- 恢复与验证方法。

变更后重新 codegen、类型检查、生产构建和受影响流程验收。

### 11.3 发布记录

至少记录 projectId、taskId、`status=active`、workbenchUrl、已验证 profile/host/team、构建产物、线上复测和已知问题。

## 13. 阶段门禁

| 阶段 | 进入条件 | 退出条件 |
| --- | --- | --- |
| G0 立项 | 有明确客户问题和决策人 | 范围、用户、主流程、成功标准确认 |
| G1 需求 | 已立项 | 五层需求模型完成 |
| G2 契约 | 需求冻结 | App、schema、access rule、数字员工 I/O、KB/文件路径确认 |
| G3 开发 | codegen 可用 | 主业务切片连接真实数据，可操作、可失败、可恢复 |
| G4 验收 | 类型和构建通过 | 真账号、真数据、正反权限和端到端链路通过 |
| G5 发布 | 获得显式批准 | 部署 active，线上路由和业务复测通过 |

上游门禁未通过，不用“先做页面看看”代替产品与数据决策。

## 14. 常见反模式

| 反模式 | 问题 | 正确做法 |
| --- | --- | --- |
| 让 AI 读完录音后一次性开发 | 概念、表、页面、权限互相冲突 | 人先完成五层需求模型 |
| 不懂业务，用 AI 代替判断 | 有页面但没有现实业务闭环 | 到真实环境走业务，做到可用表格手工表达 |
| 表、前端、数字员工无契约并行 | 上游歧义被放大 | 先冻结对象、状态、schema、权限和 I/O |
| 用 mock 证明数据已接通 | 上线后无数据、写不进或越权 | 真实 ingress 查询、写回和反向权限验证 |
| 隐藏按钮即认为安全 | API 仍可读写 | access rule 后端强制 |
| 管理员默认拥有业务权限 | 平台维护身份接触敏感数据 | 平台管理与业务角色分离 |
| 文件、知识和数据混存 | 无法检索、统计或稳定下载 | KB 存知识，文件网关存文件，ArcuBase 存业务与指针 |
| 数字员工输出直接写库 | 缺项、重复、越界和脏数据 | schema 约束、程序校验、权限预检、幂等写入 |
| 有按钮即算完成 | 点击无行为或只改本地状态 | 贯通正式写入、错误、成功和刷新 |
| 只看截图验收 | 无法证明数据和权限真实可用 | 契约、数据、操作、业务四层验收 |
| 未本地验收直接发布 | 生产环境变成调试环境 | 本地验收与发布批准两道门禁 |

## 16. 一句话总结

**Octopus W+E 项目的最佳实践，是由人先准确定义业务、权限和验收边界，再让 ArcuBase 承载可追溯数据、数字员工承载语义与执行能力、Workbench 承载人的日常作业，最后用真实业务闭环而不是截图证明交付成功。**

# 【未经验证】小章鱼 Excel 解析入库方案与耗时评估

日期：2026-10-24  
验证状态：小章鱼真实环境未验证；本地实测及假设估算见正文。  
版本：1.0  
性质：讨论纪要与技术评估；尚未在小章鱼真实团队环境完成端到端验证。

## 1. 讨论背景与需求

用户希望通过工作台上传 Excel 到知识库，对数据进行解析，再将结构化结果存入 ArcuBase，并评估整个流程需要多久。

用户已确认，本期只支持 **《6089柜止总表-自用2.xlsx》及同模板文件**。

讨论中需要区分两种时间：

- **开发工期**：把上传、解析、入库和结果展示功能开发完成需要多久。
- **单次处理耗时**：功能建成后，一份文件从上传到处理完成需要多久。

最初回答重点放在开发工期。用户随后指出传统软件十几秒即可处理，进一步明确关注的是单次执行效率、解析原理，以及小章鱼开发规范下的技术实现。

## 2. 当前结论

1. 小章鱼规范允许使用传统程序式解析，包括读入内存、按需多线程。规范没有要求逐格调用大模型，也没有规定一套专用 Excel 并行解析引擎。
2. 对固定模板，建议使用确定性程序完成表头识别、字段映射、宽表转明细、校验和入库。AI 可辅助制定、生成和维护解析规则。
3. 本机 Python 已实测：读取全部 6 个工作表，将主表展开为 297,875 条候选记录并生成 JSON，合计 **2.18 秒**。这是本地算法基准，不是小章鱼或浏览器实测。
4. 按约 30 万条候选记录入库的方案，**单次先按 1–3 分钟做条件性性能预算**。这要求具备合适的批量写入能力、网络良好，且知识库同步没有长时间等待。
5. ArcuBase 的真实批量创建入口、持续吞吐及知识库索引时间尚未验证。因此，目前不能承诺完整流程的总上限，也不能直接承诺十几秒完成。

## 3. 文件分析依据

原文件：`6089柜止总表-自用2.xlsx`。

- 文件大小：12,740,663 字节，约 12.7 MB／12.15 MiB。
- 共 6 张工作表，其中 2 张隐藏。
- 无嵌入图片、图表和外部工作簿链接，固定模板无需 OCR。
- 源文件以只读方式分析，未修改或上传。
- SHA-256：`97ce18e31e67c08a17a80a2bebebfbcd440ee26e05c74e5f5052be799aeded62`。

| 工作表 | 已识别结构 |
| --- | --- |
| 汇总 | 79 列，4,393 个含值行；第 7 行起为商品行 |
| 进销存总表 | 宽度至第 755 列，745 列有值；实际含值至第 3,550 行，第 7 行起有 3,544 条商品行 |
| Sheet1 | 113 行、2 列，业务含义待确认 |
| 客户缺货 | 无值，仅有格式 |
| 列宁村（隐藏） | 15 列，1,890 个含值行 |
| 龙头柜子运输情况（隐藏） | 19 列有值，31 个含值行 |

主表前 6 行包含柜号、发货日期、货运号、运输公司、类型和到柜日期等跨列信息。商品行与柜数量、月销量、库存和统计列混排，不能按普通 CSV 逐行搬运。

初步识别出 597 个柜数量列、123 个月销量列、3 个近期期间列。按本次选定的列分类展开，得到约 25.1 万条非零候选记录，保留显式零则约 29.8 万条。**候选记录不是最终必须写入的数据库行数**，最终数量取决于业务模型、去重和零值保留策略。

需要处理的数据问题包括：

- 全工作簿有 48,522 个公式、7,605 个保存的计算错误值。
- 汇总表另有 252 个公式包含被 `IFERROR` 遮住的 `#REF!`。
- 主表存在重复型号、缺失速达编码；汇总表与主表的 ERP 编码域不同。
- 123 个月销量列中，50 列没有明确年份，需要业务确认固定映射。

错误值应保留来源并进入异常清单；不能默认转换成零。修复历史公式、补齐业务数据与读取现有数据是不同工作范围。

## 4. 小章鱼规范规定什么

小章鱼规范主要约束应用、认证、平台能力和数据访问边界，并不强制某种内存模型或线程数。

| 层次 | 规范要求或边界 |
| --- | --- |
| Workbench | 官方 React 脚手架，TypeScript、Tailwind CSS、shadcn/ui，保留官方 Workbench 认证 |
| 文件与知识库 | 使用 `octopus` Feature 及当前客户端支持的 Host API |
| 共享业务数据 | 使用 `arcubase` Feature 和生成的 typed ingress 客户端 |
| 自研后端 | 先明确现有平台能力缺口，再决定是否需要 |
| 验收 | 真实上传、真实读写、成功后回读和可检查的结果，不能仅凭界面或代码认定跑通 |
| `compute_use` | 实际文件与长任务场景须试跑，不能直接承诺执行效果 |

Web Worker、一次读取 `ArrayBuffer`、按行块并行、解析库和批次大小，均属于本方案的工程选型，不能表述为规范强制要求。

按小章鱼 CRIDO 方法，本次闭环可表达为：

| 要素 | 本次方案 |
| --- | --- |
| Cue：触发 | 用户在工作台上传同模板 Excel |
| Reference：依据 | 已确认的模板、字段映射、编码与年份规则、校验规则 |
| Input：输入 | 原始 XLSX、文件 ID、当前团队及用户权限 |
| Do：执行 | 程序解析、校验、写入 ArcuBase、回读核对 |
| Output：结果 | 可查询的业务记录、导入批次、成功及异常数量、来源追溯 |

## 5. 建议的解析技术方案

### 5.1 执行链路

```text
Workbench 选择文件
  → 原件上传成功并关联知识库
  → 解析 Worker 读取同一原始 XLSX
  → 表头映射、宽表转明细、数据校验
  → 分批输出到写入队列
  → 通过已验证的 ArcuBase ingress 写入
  → 回读对账并显示处理结果
```

知识库承担资料保存、权限范围和检索。完整结构解析读取原始 XLSX；不能依赖知识库检索片段还原整张表。

### 5.2 内存与线程

以用户在工作台打开期间完成处理为前提，建议：

1. 将原始文件读取为一个 `ArrayBuffer`，通过 transfer 转移给 Web Worker，避免在线程间复制整份二进制。
2. 在 Worker 内完成 XLSX 解压和数据读取，界面线程处理交互与进度。
3. 读取业务所需的表头、标识、数值和错误信息，过滤格式空白，避免为无用单元格建立大量对象。
4. 先测试单 Worker。若转换阶段仍有明显耗时，再把独立商品行块分配给多个 Worker；不让每个线程复制、解压整个工作簿。
5. 结果分批输出，由受控队列消费，避免将全部明细长期放入 React 页面状态。

原始文件只有约 12.7 MB，不代表解析峰值内存也只有 12.7 MB。解压、单元格对象、转换结果和序列化都会增加内存，需要在实际浏览器中测量。

### 5.3 固定模板解析规则

建议由确定性代码执行以下步骤：

1. 检查工作表和表头是否匹配模板版本。
2. 读取柜号、运输信息、公司／地点、月份及年份，建立列映射。
3. 读取商品标识与 ERP 编码，按已确认规则处理重复和缺失。
4. 将“商品 × 柜”“商品 × 月份”等宽表区域转换为结构化明细。
5. 校验数值、日期、必填字段和关联关系，区分空白、显式零和错误值。
6. 为记录保留文件、工作表、来源行列和解析版本，支持复核。

解析规则不确定的内容进入异常清单。公式重算需要单独确认；本次基准读取的是文件已保存的值，并未重算整本工作簿。

### 5.4 ArcuBase 写入

业务数据必须走生成的 typed ingress。写入队列控制请求并发、失败记录和重试，并在成功后回读核对。

目前已确认本地合同中有 `create/update/query`；CLI 另有 Excel／CSV 导入相关命令，但尚未证明它们能直接满足本工作台、目标 App 和字段权限的批量写入需求。

因此，“批量入库”目前是设计目标。需要先验证目标入口的批量能力和吞吐，不能把几十万次单行请求并发发送等同于高效批量导入。

同文件重复导入可考虑使用文件哈希、解析版本和来源坐标识别；不同文件版本之间的覆盖、追加或业务去重规则仍待确认。

### 5.5 后台运行边界

Web Worker 是浏览器线程，不是服务端后台任务，不能承诺关闭页面后继续处理。

如果要求上传后无人值守、关闭工作台继续执行，应将同一套解析算法放到经过验证的执行宿主。Workbench 发布本身不证明拥有常驻 Python／Node 服务；需要先验证现有平台执行能力，存在缺口时再评估额外服务。

## 6. 已完成的本地性能测试

本次采用本机 Python、单进程顺序读取 ZIP／XML，并进行候选记录转换。没有使用多线程，也没有在小章鱼容器或浏览器中执行。

| 测试项 | 结果 |
| --- | ---: |
| 读取工作表数 | 6 |
| 扫描的存储单元格元素 | 3,005,374 |
| 主表候选展开记录 | 297,875 |
| 其中非零候选记录 | 251,247 |
| 候选记录 JSON 大小 | 55,074,539 字节，约 55.1 MB／52.52 MiB |
| 全部工作表读取 | 1.699 秒 |
| 主表候选记录转换 | 0.294 秒 |
| JSON 序列化 | 0.187 秒 |
| **本地合计** | **2.180 秒** |

这项测试不包含：文件上传、知识库关联和索引、完整业务口径校验、公式重算、ArcuBase 写入与回读，也不代表浏览器 Web Worker 的性能。

55.1 MB JSON 是本次测试的展开格式，不是最终必须采用的网络报文。正式字段模型、共享维度和传输格式可能改变报文大小和数据库行数。

## 7. 单次全流程需要多久

### 7.1 条件性估算

按约 30 万条候选记录展开，先以 **1–3 分钟／次**作为待验证的性能预算。成立条件包括：

- 目标 ArcuBase 具有合适的批量写入入口。
- 持续有效写入吞吐达到约每秒 5,000 条或更高。
- 网络良好，解析及校验没有出现超出预算的处理。
- 知识库同步没有长时间等待；或者索引与业务处理并行，并分别报告状态。

以下仅是记录数除以假设吞吐的计算，**不是小章鱼实测能力**：

| 假设的持续有效写入吞吐，含传输与提交 | 约 30 万条的写入耗时 |
| --- | ---: |
| 10,000 条／秒 | 约 30 秒 |
| 5,000 条／秒 | 约 60 秒 |
| 1,000 条／秒 | 约 300 秒，即 5 分钟 |

如果实际吞吐只有每秒 1,000 条，单写入就需要约 5 分钟，1–3 分钟的预算便不成立。若吞吐测量已包含网络传输，不能再重复加一次相同数据的传输时间。

### 7.2 四种完成状态

应分别记录：

1. 原件上传完成。
2. 知识库索引完成，可以检索。
3. 业务解析和校验完成。
4. 数据库写入、回读核对完成。

索引异步运行可以缩短入库等待，但不能因此把“数据库已入库”标成“知识库也已就绪”。

若索引与业务处理可以并行，时间关系大致为：

```text
入库完成时间 = 上传 + 解析校验 + 写入 + 回读

全部完成时间 ≈ 上传 + max(知识库索引,
                         解析校验 + 写入 + 回读)
```

如果业务要求先等知识库索引完成再解析，则上述环节需要串行累计。索引耗时尚未实测，因此目前不能承诺包含索引就绪的总上限。

### 7.3 与传统软件十几秒的比较

用户提出传统软件只需十几秒，应作为性能对标。

本地基准表明，程序解析本身可以很快。若要求约 30 万条明细的全流程在 15 秒内完成，仅数据库写入就至少需要每秒约 20,000 条；考虑上传、解析和回读，所需写入吞吐还要更高。

能否达到还取决于双方是否采用相同的记录粒度、数据量、网络和“完成”定义。减少不必要的展开、优化报文及选择高吞吐批量入口，都值得验证；增加解析线程不能直接解决数据库吞吐问题。

## 8. 开发工期的讨论记录

此前提出的工期，仅对应开发投入：

| 交付范围 | 初步开发工期 |
| --- | ---: |
| 固定模板最小可试用闭环 | 4–6 个工作日 |
| 增加重复导入处理、进度、重试、权限及全量验证的日常使用版本 | 8–12 个工作日 |

前提是 1 名熟悉平台的开发者配合 AI、现有权限可用、业务方及时确认口径。后台执行宿主、批量入口若存在平台缺口，或要求修复历史业务公式，需要重新评估影响。

这些天数不是单份文件的运行耗时。

## 9. 尚待确认与验证的问题

| 问题 | 对方案或性能的影响 |
| --- | --- |
| 最终需要哪些工作表、字段和业务实体 | 决定数据量，并防止汇总与明细重复入库 |
| 最终入库粒度及零值策略 | 决定是否需要约 30 万条明细 |
| 缺失年份、重复型号和编码映射 | 决定解析规则能否确定执行 |
| 使用哪个已有 ArcuBase App，或是否新建 | 决定 schema、权限和生成的 ingress |
| 目标入口能否批量创建、支持多少持续吞吐 | 决定整体耗时的主要上限 |
| 知识库原件读取、索引状态和触发方式 | 决定自动化链路与完成判定 |
| 是否要求关闭页面后继续运行 | 决定浏览器 Worker 是否足够 |
| 不同版本文件采用覆盖、追加还是业务去重 | 决定重复导入、重试和恢复策略 |

建议下一轮验证按以下顺序进行：确认最终记录模型；在真实团队测试原件上传与读取；测浏览器解析耗时和峰值内存；验证批量写入入口及代表性批次吞吐；最后用整份文件记录各阶段时间、失败恢复和回读对账结果。

完成真实端到端测试后，才能把条件性预算改为可承诺的处理时限。

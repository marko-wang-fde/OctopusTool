# 项目文档管理与文件存储标准

> 用途：供未来项目直接复用，指导项目负责人、新成员或 AI 工具建立统一、可追溯、可移交的项目文档与文件夹体系。  
> 适用范围：咨询、实施、软件开发、数字化建设、AI 应用、设备交付等以阶段性交付为目标的项目。  
> 版本：v1.0  
> 编制日期：2026-10-28  
> 实践来源：QK-2026-096 上海昱庄机械一期项目。

---

## 1. 建设目标

项目文件夹不是“资料堆放区”，而是项目事实、过程、决策和交付结果的统一证据库。标准目录应保证：

1. 新成员打开项目根目录后，5 分钟内能了解项目基本情况、当前阶段、最新版本和下一步事项。
2. 任一正式结论均能追溯到原始资料、讨论过程、确认依据和责任人。
3. 原始文件、加工文件、正式版本和临时文件互不混放。
4. 已确认的范围、计划、需求、变更、验收和交付记录不会被后续编辑覆盖。
5. 项目可在人员更换、电脑更换或长期归档后恢复工作。
6. 任何文件只有一个权威存储位置，其他位置仅保留链接、索引或明确标识的副本。
7. 项目关闭时，可以完整移交，不依赖某个人的聊天记录、电脑桌面或记忆。

## 2. 核心原则

### 2.1 一个项目，一个根目录

每个项目只建立一个正式根目录。项目相关文件不得长期散落在桌面、下载目录、聊天软件缓存、个人网盘或其他项目目录中。

项目根目录名称统一为：

`YYYYMMDD_客户简称｜项目编号｜阶段`

示例：

`20261025_上海昱庄机械｜QK-2026-096｜一期`

规则：

- `YYYYMMDD` 为项目资料库首次建立日期，不随项目进展修改。
- 客户简称应使用内部统一称呼，避免同一客户出现多个别名。
- 项目编号必须与合同、销售或内部立项编号一致。
- 分期项目必须明确“一期、二期”或“试点、推广”等阶段。
- 不在根目录名称中加入“最新版”“最终版”等不稳定描述。

### 2.2 生命周期分区

一级目录按项目生命周期编号排序，不能按个人、部门或文件格式分类。编号的意义是让所有项目具有一致的阅读顺序。

### 2.3 原件与加工件分离

- 客户提供、系统导出、录音、照片、签字件、合同扫描件等属于原始资料。
- 转写、摘要、分析、清洗、转换、裁切、重排等属于加工结果。
- 原始资料原则上只读保存，不直接修改。
- 加工结果必须另存，并说明来源。
- 对关键原件记录来源人、取得日期、原始文件名和完整性校验值。

### 2.4 正式区与临时区分离

- 正式区只保存可识别状态、可供项目使用的文档。
- 草稿、渲染图、转换缓存、实验文件、自动生成中间件统一放入 `99_临时工作/`。
- 临时目录不是长期归档目录；正式成果必须迁入对应业务目录。
- 临时目录中的唯一源码、原始数据或最终成果属于管理缺陷，必须及时纠正。

### 2.5 基线不能被覆盖

已获得确认的范围、需求、计划、预算、方案、验收标准和交付版本属于项目基线。后续修改时必须新建版本，并保留：

- 原基线文件；
- 变更原因；
- 影响分析；
- 批准人和批准日期；
- 新基线文件。

### 2.6 文件状态必须清楚

每一份重要文档至少应能识别以下状态之一：

- `草稿`：正在编制，未完成内部检查；
- `待评审`：内容已完成，等待内部或客户评审；
- `待确认`：已经评审，等待有权人员确认；
- `已确认`：已获得明确确认，可作为当前工作依据；
- `已作废`：不再使用，但为追溯而保留；
- `已交付`：已正式提交给客户或接收方；
- `已验收`：已取得有效验收证据。

“已完成”不能替代“已确认”或“已验收”。没有确认依据的文件不得自行标记为已确认。

### 2.7 一份文件只有一个权威位置

同一文件不应同时在多个正式目录中维护。需要在多个场景引用时，应在项目入口或索引中建立链接。确需复制时，必须注明：

- 哪一份是权威版本；
- 副本生成日期；
- 副本用途；
- 副本是否需要同步更新。

## 3. 标准一级目录

所有标准项目至少建立以下结构：

```text
项目根目录/
├── README_项目入口.md
├── 00_立项与商务/
├── 01_调研与原始资料/
├── 02_需求与方案/
├── 03_开发实施/
├── 04_过程管理/
├── 05_测试与验收/
├── 06_发布与交付/
├── 07_运维与维保/
└── 99_临时工作/
```

项目暂未进入某一阶段时，对应目录可以为空，但不得删除或改变编号。若确实不适用，应在项目入口中说明原因。

### 3.1 `README_项目入口.md`

这是项目唯一入口，必须位于根目录。至少包含：

| 项目 | 必填内容 |
| --- | --- |
| 基本信息 | 项目编号、客户、阶段、开始日期、项目状态 |
| 责任信息 | 我方负责人、客户负责人、验收人、技术负责人 |
| 范围信息 | 当前范围、排除项、范围确认依据 |
| 进度信息 | 当前阶段、关键里程碑、下一步动作 |
| 版本信息 | 最新确认需求、当前上线版本、代码提交号 |
| 环境信息 | 代码仓库、平台、测试环境、生产环境的访问入口 |
| 待办信息 | 未完成事项、责任人、计划日期 |
| 风险信息 | 当前重大问题、风险和待决策事项 |
| 存储信息 | 权威存储位置、备份位置、最近备份和恢复验证日期 |
| 凭据信息 | 凭据获取方式；不得在入口中直接写密码和密钥 |
| 关键索引 | 范围、需求、方案、日报、决策、验收、交付等最新文件链接 |

项目入口必须随着关键状态变化更新，不得只在建项时填写一次。

### 3.2 `00_立项与商务/`

保存项目授权与商务边界，包括：

```text
00_立项与商务/
├── 01_立项与授权/
├── 02_合同与报价/
├── 03_项目范围与计划/
├── 04_干系人与通讯录/
└── 05_商务澄清与往来/
```

管理要求：

- 合同、报价和付款信息按权限控制，不默认向全体成员开放。
- 口头承诺必须转成书面记录，并标明是否已获有权人员确认。
- 商务范围、技术范围和实际交付范围存在差异时，必须建立澄清清单。
- 项目计划应区分“批准基线”和“当前预测”，不能用新预测覆盖原计划。

### 3.3 `01_调研与原始资料/`

保存调研输入、客户原件、访谈记录和现场证据，包括：

```text
01_调研与原始资料/
├── 01_调研准备/
├── 02_客户背景/
│   └── 原始资料/
├── 03_访谈纪要/
├── 04_系统走查/
├── 05_现场照片与录音/
└── 06_调研结果/
```

访谈或会议原始资料按“一场一组”保存：

```text
YYYYMMDD_HHMM_主题/
├── 归档清单.md
├── 录音或录像原件
├── 文字转写
├── 纪要概括
├── 说话人识别说明
└── 分析材料
```

管理要求：

- 录音、照片、系统截图保留原格式和原始字节。
- 转写和纪要不得替代原始记录。
- 原始事实、受访者意见、我方判断和待验证假设必须明确区分。
- 引用访谈结论时，尽量保留时间戳或原文位置。
- 每组资料维护 `归档清单.md`，上级目录维护总索引。
- 涉及个人信息、商业秘密、系统账号或敏感画面的资料应提高权限等级。

### 3.4 `02_需求与方案/`

保存从调研结论到可确认方案的全部正式工作成果，包括：

```text
02_需求与方案/
├── 01_需求清单与范围/
├── 02_业务流程与用例/
├── 03_总体方案/
├── 04_详细设计/
├── 05_数据接口与权限/
├── 06_评审与确认记录/
└── S01_场景或模块名称/
```

管理要求：

- 需求、方案和验收标准应相互对应。
- 每项重要需求应能追溯到来源、责任人、优先级、状态和确认依据。
- 待确认方案不得作为已承诺交付范围。
- 排除项必须显式记录，避免后期被误认为遗漏。
- 场景或模块一经编号，在需求、开发、测试和交付目录中保持同一编号。

### 3.5 `03_开发实施/`

保存实施过程中的源码入口、平台配置、数据工具和部署记录，包括：

```text
03_开发实施/
├── S01_场景或模块名称/
│   ├── app/
│   ├── platform/
│   ├── data-tools/
│   └── README.md
├── S02_场景或模块名称/
├── 90_公共组件/
└── 91_环境与部署记录/
```

管理要求：

- 源代码以 Git 仓库为权威来源，项目资料库保存仓库地址、分支策略、版本标签和提交号。
- 不把密码、密钥、访问令牌写入文档或源码；只记录安全的凭据获取方式。
- 平台中人工配置的流程、提示词、权限和数字员工设置必须有可导出版本或配置清单。
- 数据清洗、迁移和批处理应保留输入说明、脚本、执行日期、执行人、结果和异常记录。
- 测试环境与生产环境必须明确区分。

### 3.6 `04_过程管理/`

保存项目运行与治理记录，包括：

```text
04_过程管理/
├── 01_会议纪要/
├── 02_日报周报/
├── 03_计划与进度/
├── 04_RAID台账/
├── 05_决策记录/
├── 06_变更记录/
├── 07_沟通与汇报/
└── 08_复盘与经验/
```

其中 RAID 指：

- `R`：风险，尚未发生但可能发生；
- `A`：假设，需要验证的前提；
- `I`：问题，已经发生且需要处理；
- `D`：依赖，项目受其制约的外部条件。

管理要求：

- 每项承诺必须有动作、责任人和日期；未知项标记 `TBD`，不得编造。
- 决策记录必须包含背景、选项、结论、决策人、日期和影响。
- 变更记录必须包含原范围、变更内容、原因、影响、审批结果和更新的基线。
- 日报、周报应报告结论、偏差、风险和下一步，不只是罗列活动。
- 微信、邮件或口头形成的关键决定，应整理为正式记录并注明来源。

### 3.7 `05_测试与验收/`

保存测试设计、测试结果、缺陷、验收标准和签认凭证，包括：

```text
05_测试与验收/
├── 01_验收标准/
├── 02_测试计划与用例/
├── 03_测试数据与证据/
├── 04_缺陷与整改/
├── 05_用户验收/
└── 06_签字盖章原件/
```

管理要求：

- 测试结果必须对应具体版本、环境、日期和执行人。
- 截图应能说明测试步骤、输入、结果和时间，不能只保留孤立画面。
- 缺陷关闭必须保留复测证据。
- 扫描件或照片属于验收原件；为便于检索，可另建文字版，但文字版不得替代原件。
- “已提交验收”与“已通过验收”必须区分。

### 3.8 `06_发布与交付/`

保存对外发布和正式移交材料，包括：

```text
06_发布与交付/
└── YYYYMMDD_vX.Y_版本名称/
    ├── 01_发布说明/
    ├── 02_交付文件/
    ├── 03_部署与回退/
    ├── 04_培训材料/
    ├── 05_交付清单/
    └── 06_接收确认/
```

管理要求：

- 每次正式发布单独建组，不覆盖历史发布。
- 发布组必须说明版本号、代码提交号、配置版本、数据库或数据版本、发布日期和适用环境。
- 交付清单应逐项记录文件、数量、版本、接收人、接收日期和结果。
- 发布前应具备回退方案；无法回退时必须明确风险和批准人。

### 3.9 `07_运维与维保/`

保存项目上线后的运行资料，包括：

```text
07_运维与维保/
├── 01_运维手册/
├── 02_账号权限与交接/
├── 03_监控与巡检/
├── 04_故障与事件/
├── 05_版本与配置变更/
├── 06_服务记录/
└── 07_质保结束与移交/
```

管理要求：

- 故障记录应包含发生时间、影响、原因、处理、恢复时间和预防措施。
- 生产配置变更必须留痕，并能对应到批准记录。
- 运维交接要明确服务边界、联系人、响应方式、到期时间和遗留事项。

### 3.10 `99_临时工作/`

仅用于草稿、试验、中间渲染、批量转换、缓存和一次性工作文件。

推荐二级结构：

```text
99_临时工作/
├── YYYYMMDD_任务名称/
├── render/
├── tmp/
└── 待归档/
```

管理要求：

- 临时任务目录以日期和任务命名，避免出现大量含义不明的文件。
- 临时区不作为最终交付来源。
- 每周检查一次，将正式成果迁入对应目录。
- 删除前先确认其中不存在唯一原件、唯一源码或尚未归档的正式成果。
- 项目关闭前必须完成清理；有追溯价值的过程材料可压缩后归档，其余按规则删除。

## 4. 文件命名标准

### 4.1 通用格式

正式文件优先采用：

`YYYYMMDD_项目或客户_主题_版本_状态.扩展名`

示例：

- `20261027_上海昱庄机械_一期范围与验收标准_v1.0_待确认.pdf`
- `20261028_QK-2026-096_项目周报_v1.0_已发布.md`
- `20261030_S01_AI项目助理_测试报告_v1.2_已确认.docx`

### 4.2 日期规则

- 统一使用 8 位日期 `YYYYMMDD`。
- 有明确时间顺序要求的访谈、会议、录音使用 `YYYYMMDD_HHMM`。
- 文件日期表示本版本形成日期，不表示内容覆盖周期；周期另在文档中写明。

### 4.3 版本规则

- `v0.x`：草稿、内部讨论或待确认版本。
- `v1.0`：首次正式确认、发布或交付版本。
- `v1.1`、`v1.2`：不改变核心边界的小幅修订。
- `v2.0`：范围、结构、接口、核心逻辑或交付边界发生重大变化。
- 正式文件不使用“最终版”“最终最终版”“最新版”等名称。
- 被替代的正式版本不得删除，应标记为历史版本或已作废。

### 4.4 名称用词

- 文件名应描述内容，不使用“新建文档”“未命名”“副本”等默认名称。
- 同一客户、项目、场景和人员使用统一称呼。
- 少用特殊符号；推荐中文、英文、数字、下划线和短横线。
- 避免文件名过长；详细背景写入文档正文或归档清单。

## 5. 文档状态与版本流转

标准流转为：

`草稿 → 待评审 → 待确认 → 已确认 → 已交付／已验收`

特殊流转为：

`任一状态 → 已作废`

规则：

1. 文件进入待确认状态前，必须完成内部检查。
2. 已确认文件必须记录确认人、确认日期和确认方式。
3. 邮件、企业微信、会议等确认方式应保留可验证证据。
4. 已确认文件需要修改时，不直接覆盖，先发起变更并创建新版本。
5. 新版本生效后，在索引中把它标为当前版本，同时保留历史版本链接。
6. 文件名状态与正文状态必须一致。

## 6. 归档清单标准

以下情况必须建立 `归档清单.md`：

- 一组访谈、会议录音或视频；
- 一批现场照片或系统截图；
- 客户一次性提供的一批原始材料；
- 测试、验收或交付文件组；
- 项目阶段归档包；
- 需要证明文件完整性和来源的资料。

归档清单至少包含：

| 字段 | 说明 |
| --- | --- |
| 所属项目 | 项目编号和名称 |
| 资料主题 | 本组材料说明 |
| 来源 | 提供人、系统或取得渠道 |
| 取得时间 | 文件收到或采集时间 |
| 整理人 | 实际归档人员 |
| 整理日期 | 完成归档日期 |
| 文件索引 | 文件名、类型、用途、状态 |
| 原始文件名 | 归档前名称 |
| 归档路径 | 在项目中的相对路径 |
| 完整性信息 | 文件大小、页数、数量、SHA-256 等 |
| 缺失项 | 应有但尚未取得的材料 |
| 注意事项 | 权限、隐私、疑点、使用限制 |

关键原件建议记录 SHA-256 校验值，用于证明归档后未被修改。

## 7. 文件存储方案

### 7.1 三层存储模型

项目采用“工作区—协作区—备份区”三层模型。

| 层级 | 作用 | 权威性 | 管理要求 |
| --- | --- | --- | --- |
| 工作区 | 日常编辑、分析、制作和测试 | 过程性 | 可在个人电脑，但必须定期同步 |
| 协作区 | 团队共享、正式资料和当前版本 | 项目权威来源 | 使用公司批准的共享盘、文档平台或项目空间 |
| 备份区 | 防误删、防设备损坏、防平台故障 | 恢复来源 | 与协作区独立，按计划备份并验证恢复 |

协作区是项目文档的权威来源。个人电脑不是唯一存储位置，聊天软件也不是项目资料库。

### 7.2 3-2-1 备份原则

关键项目资料至少满足：

- 保留 3 份副本；
- 使用 2 种不同介质或存储系统；
- 至少 1 份位于不同设备或独立位置。

推荐组合：

1. 团队协作区中的主副本；
2. 项目负责人的受控同步副本；
3. 公司备份系统、独立存储或离线加密归档副本。

### 7.3 备份频率

| 内容 | 建议频率 |
| --- | --- |
| 日常文档和过程记录 | 每日同步 |
| 需求、方案、计划、代码和配置 | 每次重要修改后同步 |
| 正式确认、验收和交付资料 | 形成后立即备份 |
| 全项目增量备份 | 每日 |
| 全项目完整备份 | 每周或每个里程碑 |
| 长期归档包 | 阶段结束和项目关闭时 |

### 7.4 恢复验证

“备份成功”不等于“可以恢复”。项目至少在以下节点执行恢复抽查：

- 项目启动后；
- 重要里程碑前；
- 正式上线前；
- 项目关闭前；
- 存储平台或电脑更换后。

恢复验证应记录：验证日期、备份来源、抽查文件、恢复结果、异常和处理人，并更新项目入口。

### 7.5 大文件与二进制文件

录音、视频、照片、PPT、PSD、设计源文件、安装包和压缩包通常占用空间较大，应遵守：

- 原件只保存一份权威副本，不在多个正式目录重复复制。
- 大文件集中存放，并在使用位置建立索引。
- 生成的大量页面渲染图、预览图和缓存放在临时区，不进入长期正式存储。
- 压缩包不能代替可浏览的正式目录；归档压缩包应附文件清单和校验值。
- 关键可编辑源文件与导出的 PDF、图片等发布格式成对保存。

### 7.6 源代码与项目文档分工

- 源代码、脚本和配置文件由 Git 管理版本。
- 项目文档库记录仓库地址、默认分支、发布标签、提交号和部署版本。
- 大型数据集、密钥和个人隐私数据不得直接提交到普通代码仓库。
- 正式发布时，交付版本必须能对应到唯一代码提交和唯一配置版本。

### 7.7 凭据与敏感信息

- 密码、API Key、密钥、令牌不得存入普通文档、聊天记录或代码文件。
- 项目文档只记录凭据保管系统、申请方式、权限范围和负责人。
- 敏感文件按最小权限原则开放。
- 人员离项、角色变更或项目结束后应及时回收权限。
- 对外共享前检查个人信息、客户数据、报价、合同、账号和系统截图。

## 8. 权限管理规则

建议按角色设置权限，而不是逐个文件临时授权。

| 角色 | 默认权限 |
| --- | --- |
| 项目负责人 | 全项目管理，含权限、归档和移交 |
| 项目成员 | 与工作相关目录的编辑权限 |
| 商务人员 | 立项、合同、报价和商务澄清目录 |
| 技术人员 | 需求、开发、测试、发布和运维目录 |
| 客户或外部合作方 | 经批准的指定目录或交付包，只给必要权限 |
| 审计或管理人员 | 按需要提供只读权限 |

特殊规则：

- 合同、报价、个人信息、生产数据和凭据相关资料单独控制。
- 对外共享不直接开放整个项目根目录。
- 临时外链应设置有效期；到期后关闭。
- 每个里程碑和人员变动时复核一次权限。
- 项目关闭后，大多数成员权限调整为只读或取消。

## 9. 日常维护机制

### 9.1 每日

- 将聊天软件、邮件、下载目录中的项目文件归入正式目录。
- 更新当日会议、问题、决策和待办。
- 确认当天重要文件已同步到协作区。
- 重要结论补充来源和确认依据。

### 9.2 每周

- 更新项目入口中的状态、最新版本、风险和下一步。
- 清理 `99_临时工作/`，迁移正式成果。
- 检查是否存在重复文件、无意义文件名或散落文件。
- 检查已确认基线是否被覆盖。
- 检查 RAID、决策和变更记录是否完整。
- 确认备份结果，必要时抽查恢复。

### 9.3 里程碑节点

- 冻结当期范围、计划、方案和验收标准。
- 形成阶段归档清单。
- 确认当前版本、批准人和日期。
- 备份阶段成果并进行恢复抽查。
- 记录遗留问题、风险、责任人和下一阶段准入条件。

### 9.4 项目关闭

- 确认交付和验收凭证齐全。
- 完成合同、费用、采购和资源关闭记录。
- 移交运维资料、账号权限和遗留事项。
- 清理临时文件和重复副本。
- 形成项目关闭报告、复盘和经验记录。
- 生成长期归档包及文件清单。
- 完成最终备份与恢复验证。
- 将项目目录调整为只读，保留明确的档案负责人和保存期限。

## 10. AI 工具建设目录时的规则

未来由 AI 工具新建或整理项目目录时，应向 AI 明确提供：

- 项目名称、项目编号、客户名称和阶段；
- 项目建立日期；
- 项目类型及是否包含软件开发、设备交付或长期运维；
- 已有文件所在位置；
- 哪些文件属于原件，禁止修改；
- 哪些目录或文件含敏感信息；
- 当前负责人、客户负责人和验收人；
- 已确认范围、当前阶段和现有基线；
- 需要保留的历史版本和确认依据。

AI 工具必须遵守以下边界：

1. 先盘点、后搬移，不凭文件名猜测并删除资料。
2. 不修改原始文件内容，不覆盖已确认文件。
3. 不把草稿标记为已确认，不虚构负责人、日期或审批结果。
4. 无法判断归属的文件放入 `99_临时工作/待归档/`，并列出待确认清单。
5. 搬移后更新项目入口、索引和归档清单。
6. 对关键原件保留原文件名、来源和校验值。
7. 发现重复文件时，先比较内容和版本，再提出保留方案。
8. 任何删除、覆盖或批量重命名操作，必须在执行前明确范围并取得授权。
9. 建设完成后必须输出目录树、异常清单、缺失信息和验收结果。

## 11. 建设完成验收标准

新人或 AI 工具完成项目目录建设后，应逐项检查：

### 11.1 结构

- [ ] 项目根目录名称符合标准。
- [ ] `README_项目入口.md` 位于根目录。
- [ ] `00` 至 `07` 和 `99` 一级目录完整、编号连续。
- [ ] 二级目录与项目实际类型匹配。
- [ ] 场景或模块编号在需求、开发、测试和交付中保持一致。

### 11.2 内容

- [ ] 项目入口包含负责人、当前阶段、范围、最新版本和待办。
- [ ] 原始资料与加工结果分开。
- [ ] 草稿、正式成果和临时文件分开。
- [ ] 关键资料有归档清单和来源记录。
- [ ] 已确认基线和历史版本得到保留。
- [ ] 需求、方案、测试和验收之间可以追溯。
- [ ] 决策、变更、风险、问题和依赖有记录。

### 11.3 存储与安全

- [ ] 已明确协作区中的权威存储位置。
- [ ] 项目不是只存在于个人电脑或聊天软件中。
- [ ] 已明确备份位置、频率和负责人。
- [ ] 已执行至少一次恢复验证并记录结果。
- [ ] 密码、密钥和令牌未写入普通文档。
- [ ] 敏感目录权限符合最小权限原则。

### 11.4 质量

- [ ] 文件名称统一，无“最终最终版”等模糊名称。
- [ ] 重要文件有日期、版本和状态。
- [ ] 无多个位置同时维护同一权威文件。
- [ ] 临时区没有唯一原件或唯一正式成果。
- [ ] 入口中的链接有效，关键文件能够打开。
- [ ] 缺失资料、待确认事项和异常已单独列出。

## 12. 本项目实践提炼

QK-2026-096 上海昱庄机械一期项目中，以下做法值得复用：

1. 使用 `00—07` 按项目生命周期组织文件，使调研、需求、开发、过程、验收、交付和运维自然衔接。
2. 在根目录设置 `README_项目入口.md`，集中呈现项目状态和关键文件索引。
3. 访谈资料采用“一场一组”，把原文、纪要、说话人说明、分析和归档清单放在一起。
4. 原始照片、扫描件与可检索文字版并存，兼顾证据真实性和后续检索使用。
5. 对关键原件记录来源路径、文件大小和 SHA-256，增强完整性与追溯能力。
6. 使用 `99_临时工作/` 隔离 PPT 渲染、图片生成、脚本和中间版本，避免正式目录被过程文件淹没。
7. 在日报中区分事实、风险、问题、待决策和下一步动作，避免把调研完成误写成范围已确认或项目已开工。

同时，本项目也说明了以下风险：

- 临时生成物可能远大于正式资料，必须定期清理并避免重复保存。
- `output/`、`tmp/`、渲染检查目录与正式交付目录容易混淆，应统一纳入 `99_临时工作/` 或明确其临时属性。
- 空目录只能表达规划，不能证明项目资料齐备；必须在项目入口说明当前阶段和缺失项。
- 待确认文档、正式范围和已交付成果必须明确区分，不能仅凭文件名中的版本号判断有效性。
- 项目入口中的负责人、备份位置、恢复验证和环境信息若长期为“待填写”，会直接影响项目移交和恢复能力。

## 13. 最低执行要求

即使是短周期、小规模项目，也不得省略以下内容：

1. 一个标准项目根目录；
2. 一个持续更新的项目入口；
3. 原始资料与加工资料分离；
4. 明确的范围、需求和验收依据；
5. 决策、问题、风险和变更记录；
6. 正式交付清单和接收证据；
7. 独立备份及恢复验证；
8. 项目关闭后的只读归档。

项目越复杂、风险越高、参与方越多，越应加强版本、权限、基线、变更、验收和备份控制，而不是增加更多没有实际用途的空文件夹。

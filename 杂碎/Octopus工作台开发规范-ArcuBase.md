# Octopus 工作台开发规范（ArcuBase）

本文仅整理《工作台开发问题复盘与技术交流》中的明确内容，不补充会议未讨论的开发、测试、安全或运维要求。

## 1. 适用范围

本规范适用于以下组合开发场景：

- Octopus 工作台（Workbench）
- ArcuBase 数据表及权限
- 数字员工
- Skill
- Octopus 平台 API
- 任务板等平台资源

## 2. 总体原则

### 2.1 先理解业务，再进入开发

开发人员必须先理解业务实际如何运行，明确业务中的前后关系，不能在不了解业务的情况下直接让 AI 生成系统。

开发人员应达到以下要求：

- 能在脑中形成完整的业务画面。
- 能说明业务中有哪些参与者、业务对象和处理过程。
- 能说清楚系统在客观世界中解决什么问题。
- 能用 Excel、表格或其他方式把业务逻辑表达清楚。
- 能判断 AI 给出的业务结构、数据结构和实现方案是否正确。

AI 是开发工具，不能代替开发人员定义问题、边界和业务逻辑。（01:08:31—01:16:21）

### 2.2 不得将业务和数据设计完全交给 AI

不得直接让 AI 自行决定：

- 业务概念。
- 业务对象之间的关系。
- ArcuBase 表结构。
- ArcuBase 字段。
- 组织权限与角色权限的选择。
- 数字员工与 Skill 的业务边界。

开发人员必须理解这些内容，并能够逐项检查。（01:05:12—01:08:16）

### 2.3 使用官方开发路径

开发过程中应优先使用：

- Octopus 官方开发资料。
- GitHub 中的最新工具和文档。
- 官方 Skill。
- `create-workbench-app`。
- 官方提供的 Features 和 API 包。

使用官方 Skill 时，应按 Skill 已经描述的开发路径执行，不需要重新让 AI 自行选择技术栈。（00:14:36—00:25:47）

## 3. 标准开发流程

开发工作按照以下六个步骤开展。

### 3.1 第一步：定义业务概念

首先定义整个业务体系中的核心概念。

概念包括但不限于：

- 用户。
- 内部用户。
- 外部用户。
- 客户。
- 管理端。
- 用户端。
- 订单。
- 子订单。
- 项目。
- 任务。
- 其他业务中的核心名词。

需要明确每个概念的含义，以及概念之间的关系。

ArcuBase 的库表结构从概念定义阶段就已经开始形成。后续步骤是在不断细化第一步中定义的内容。（00:48:32—00:49:38、00:52:06—00:52:45）

### 3.2 第二步：定义用例

每个用例必须明确：

- 谁来执行。
- 在什么时间或条件下执行。
- 通过什么方式执行。
- 执行什么事情。
- 正确结果是什么。
- 错误结果是什么。

用例是产品设计中必须具备的内容。（00:49:38—00:50:21）

### 3.3 第三步：定义约束

需要说明用户执行用例时受到的各种约束，例如：

- 哪些信息不能看到。
- 哪些操作必须登录后才能执行。
- 不同人员能访问哪些数据。
- 哪些敏感信息不能向特定用户展示。

会议中举出的例子包括：用户购买商品时不能看到成本价，只有登录用户才能执行特定操作。（00:50:21—00:50:48）

### 3.4 第四步：设计 Sitemap

需要明确系统通过哪种方式提供服务：

- Workbench 工作台。
- IM。
- 其他系统入口。

如果通过 Workbench 提供服务，需要明确：

- 有哪些页面。
- 有哪些路由。
- 哪些页面可以访问。
- 各页面提供什么功能。

Sitemap 用于形成系统整体功能列表和前端结构。（00:50:51—00:51:45）

### 3.5 第五步：完成业务与平台资源映射

需要把 Sitemap 中的功能映射到具体资源。

逐项判断：

- 哪些功能连接 ArcuBase。
- 哪些功能直接调用 Octopus API。
- 哪些功能使用任务板。
- 哪些功能由数字员工执行。
- 哪些能力通过 Skill 实现。
- 哪些功能现有平台没有，需要单独开发后端应用。

该步骤用于明确业务功能与平台资源之间的对应关系。（00:51:07—00:52:06）

### 3.6 第六步：执行开发

前五个步骤完成后，再进入具体开发。

开发内容包括：

- 创建和配置 ArcuBase。
- 创建 Workbench 应用。
- 开发页面和功能。
- 创建数字员工。
- 编写 Skill。
- 调用平台 API。

不得在概念、用例、约束、Sitemap 和资源映射尚未明确时，直接要求 AI 一次性完成全部开发。（01:03:08—01:05:12）

## 4. ArcuBase 开发规范

### 4.1 先建立表结构，再开发 Workbench

业务系统的开发顺序为：

1. 在 ArcuBase 中建立表结构。
2. 创建 Workbench 应用。
3. 将 ArcuBase Schema 拉取到本地。
4. 基于 Schema、平台 API 和业务需求实现页面与功能。

Workbench 不应在没有确定 ArcuBase 表结构的情况下先行开发。（00:17:10—00:20:39）

### 4.2 开发人员必须掌握表和字段

开发人员必须能够明确：

- 系统有哪些表。
- 每张表有哪些字段。
- 字段分别表示什么。
- 表之间是什么关系。
- 数据挂在哪个业务对象上。

不能只要求 AI“设计一个数据库”，而自己不知道具体字段。（01:05:12—01:05:43）

### 4.3 表结构由业务决定

表结构没有脱离业务的固定答案。

例如，订单、子订单、地址和物流单之间的关系，需要根据以下业务情况决定：

- 是否存在分销。
- 是否需要二次分拣。
- 是否属于一件代发。
- 是否涉及多个供应商。
- 数据应挂在订单还是子订单上。

数据库设计的前提是理解客户业务。（00:39:52—00:42:57）

### 4.4 可参考成熟开源系统

对于 CRM 等常见系统，可以：

1. 询问 AI 有哪些较好的开源系统。
2. 下载开源系统源码。
3. 让 AI 分析其表结构和数据库设计。

会议明确提出，不应仅依靠经典数据库设计书籍解决实际系统的业务建模问题。（00:36:33—00:39:04）

### 4.5 ER 图的使用

如果开发人员已经能够画出 ER 图，可以把 ER 图交给 AI。

使用 ER 图时：

- 可以提供图片。
- 更推荐提供源文件。
- 可以使用 UML 或数据库设计工具产生的源文件。

如果概念、用例、约束、Sitemap 和资源映射已经定义清楚，库表结构也可以从这些内容中逐步形成，不要求必须额外制作 ER 图。（00:42:57—00:43:37、00:52:06—00:52:45）

### 4.6 ArcuBase 审批流名称

ArcuBase 中由人参与执行的流程，应称为“审批流”。

需要与系统之间自动执行、定时调度的工作流区分，避免与 N8N 一类自动工作流混淆。（00:21:18—00:22:17）

## 5. ArcuBase 权限规范

### 5.1 管理员权限

Team 管理员应具备相应的 ArcuBase 管理权限。

如果管理员没有相应权限，而只有创建者可以操作，应作为 Bug 提交。（00:12:21—00:12:53）

### 5.2 权限模型由人明确

权限配置不能完全交给 AI。

开发人员需要明确：

- 权限是否通过组织结构隔离。
- 权限是否通过角色隔离。
- 什么情况下使用组织结构。
- 什么情况下使用角色。

ArcuBase CLI 可以告诉 AI 平台有哪些权限能力，但不能自行判断具体业务应采用哪种权限方式。（01:07:53—01:08:29）

### 5.3 权限配置方式

权限最好由人配置，或者由人先明确权限设计，再交给 AI 执行。

不得只向 AI 提供“配置权限”这类笼统要求。（01:07:53—01:08:29）

## 6. Workbench 工程规范

### 6.1 使用标准脚手架

Workbench 应使用 `create-workbench-app` 创建。

NPM 上的包与 GitHub 中的对应工具属于同一套内容，NPM 包用于执行应用创建。（00:14:36—00:15:40）

### 6.2 默认技术栈

`create-workbench-app` 已内置经过验证的前端技术栈，包括：

- React。
- Vite。

Workbench 开发优先采用以下组合：

- React。
- TypeScript。
- Tailwind CSS。
- `shadcn/ui`。

该组合在 AI 开发中的成功率较高。（00:19:37—00:20:39、00:23:06—00:24:18）

### 6.3 组件选择顺序

页面组件应优先从 `shadcn/ui` 生态中选择。

选择顺序为：

1. 先在 `shadcn/ui` 生态中查找。
2. 现有组件能够满足需求时，直接使用。
3. 只有现有生态不能满足需求时，才允许选择其他技术或组件。

使用官方 Skill 时，上述要求已经包含在 Skill 中；只有在没有使用 Skill，或者 Skill 内容在长上下文中丢失时，才需要重新向 AI 明确技术栈限制。（00:24:04—00:26:12）

### 6.4 Features 配置

创建 Workbench 应用时，应根据需要指定 Features。

会议中明确提到的 Features 包括：

- 任务板能力。
- 数据表能力。
- 数字员工能力。
- 发起数字员工对话等能力。

指定 Feature 后，对应的代码包和 API 会进入项目。（00:15:40—00:17:10）

### 6.5 登录与鉴权

Workbench 脚手架会与 Octopus 当前用户权限打通。

- 在部署环境中，登录状态自动打通。
- 在本地开发环境中，会自动打开登录页面。
- 登录后，应用可以按所选 Features 访问相应的 Octopus 资源。（00:15:40—00:17:10）

### 6.6 Schema 同步

ArcuBase 表创建完成后，Workbench 开发工具会读取表的 Schema，包括：

- 表清单。
- 字段清单。
- 表结构。

Schema 拉取到本地后，AI 基于表结构和 API 实现页面、卡片及其他 UI。（00:17:10—00:18:18）

## 7. UI 开发规范

### 7.1 原型应采用标准组件体系

在设计页面样式时，应直接按照 `shadcn/ui` 的组件和样式进行设计。

应尽量使用其自带的：

- 表格。
- 卡片。
- 图表。
- 其他界面控件。

这样可以减少原型与最终实现之间的差异。（00:46:03—00:47:09）

### 7.2 Figma 原型

如果需要提高页面还原准确度，可以使用 Figma。

Figma MCP 能向 AI 提供：

- 控件信息。
- 控件位置。
- 页面结构。

会议中的有限实践表明，Figma 的页面还原准确度较高，但会消耗相应的使用额度。（00:44:59—00:45:57）

### 7.3 像素级对比

当页面与原型存在明显偏差时，可以：

1. 为 AI 设置明确目标。
2. 让 AI 进行像素级对比。
3. 根据对比结果持续调整。

这种方式可以执行，但耗时和 Token 消耗较大，可能运行十几个到二十几个小时。（00:44:23—00:44:59）

## 8. Skill 使用规范

### 8.1 优先使用官方 Skill

官方 Skill 已描述：

- 推荐开发路径。
- 技术栈。
- 工具使用方式。
- 平台能力的调用方法。

使用 Skill 后，不应再让 AI 重新选择整套实现路径。（00:24:18—00:25:47）

### 8.2 Skill 内容丢失时重新补充

如果对话上下文过长，导致 Skill 内容被上下文压缩或忽略，应重新加载或补充 Skill 中的要求。（00:25:38—00:25:56）

### 8.3 工具路径写入 Skill

工具安装在数字员工 Home 目录后，应在 Skill 中告诉数字员工：

- 工具安装位置。
- 工具的绝对路径。
- 如何调用工具。

这样数字员工后续执行时才能找到工具。（00:05:43—00:06:42）

## 9. 数字员工 Home 配置规范

Octopus 为数字员工提供三种 Home 策略：

- 以当前对话用户身份创建 Home。
- 以数字员工自身身份创建 Home。
- 全局共享同一个 Home。

对于需要由多个用户共同调用、但工具和运行环境应归属于该数字员工的场景，应使用数字员工自身的 Home。

工具应安装到该数字员工自己的 Home 目录，并在 Skill 中写明绝对路径。（00:04:42—00:06:42）

## 10. 开发资料与版本规范

### 10.1 开发资料作为 AI 知识库

Octopus 开发代码库和文档库应：

1. 克隆到本地。
2. 作为本地知识库。
3. 在新项目开始时交给 AI 阅读。
4. 由 AI 结合说明书分析项目应该如何开发。

这些资料主要用于 AI，不要求开发人员逐页阅读所有实现细节。（00:30:42—00:34:25）

### 10.2 团队共同维护

开发资料应由团队共同维护。

发现现有文档缺少内容时，应进行补充，目标是让新开发人员可以直接把资料交给 AI，而不需要重新进行完整口头培训。（00:34:25—00:35:07）

### 10.3 使用最新且相互匹配的版本

Octopus 各工具和包之间存在紧密的版本依赖，包括：

- ArcuBase 接口。
- 任务板接口。
- 登录状态。
- Workbench 包。
- 其他平台能力。

开发时应使用最新版本，并保证相关组件来自同一个兼容版本组合。平台更新时，相关组件应一起更新。（00:35:08—00:36:15）

## 11. AI 开发执行规范

### 11.1 禁止一次性完成全部开发

不得在上游设计未完成时，要求 AI 一次性完成：

- ArcuBase。
- Workbench。
- 数字员工。
- Skill。
- Spec。
- Graph。

会议复盘表明，这种方式会造成 AI 反复尝试、长时间运行和 Token 浪费。（01:03:08—01:05:12）

### 11.2 存在依赖时不宜拆开

ArcuBase、Workbench、数字员工和 Skill 之间存在依赖关系。

如果拆成多个独立对话并行执行，可能出现：

- 下游依赖上游结果。
- 不同对话得出不一致结论。
- 后续整体返工。

因此，存在依赖关系的部分不宜完全拆开独立开发。（01:06:30—01:07:25）

### 11.3 调整开发顺序

开发顺序必须体现前后依赖：

1. 研究业务。
2. 定义概念和用例。
3. 明确约束。
4. 设计 ArcuBase。
5. 明确权限。
6. 设计 Sitemap。
7. 完成资源映射。
8. 创建 Workbench。
9. 开发数字员工和 Skill。
10. 完成页面与平台资源连接。

不得跳过前面的业务和数据定义，直接进入 Coding。（01:05:12—01:16:21）
